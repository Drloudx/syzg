# 贡献与提交规范

>
> **何时读**：准备提交、写提交信息或判断改动范围时。
> **何时更新**：提交格式、验收要求或提交范围约定变化时。

**核对时间**：2026-10-08

本文规定**改动怎么落地**：提交时机、提交信息格式与写作要求、提交范围约定。
面向在本仓库改代码的人（含 AI 助手）；项目本身怎么跑、各页面做什么见 [README](../../README.md) 与 [DOMAIN](./DOMAIN.md)。

## 一、提交时机

改完 → 与范围匹配的验证通过 → 写当日开发日志 → 权威文档同步完成 → 再 commit。

- 完整发布验收用 `npm run verify`（含数据再生成与生产构建）；
- 纯文档改动检查相对链接、UTF-8 编码与差异格式即可；
- 不要只更新 `index.html` 而遗漏它引用的资源。

## 二、提交信息格式

```
{type}({scope}): {一句话摘要}

更新
- 新增或改变的行为、数据、接口

优化
- 性能、体积、结构或可维护性改进（不改变外部行为）

修复
- 缺陷的现象与修正
```

- **`type`**：`feat`（新功能）/ `fix`（修缺陷）/ `refactor`（重构）/ `perf`（性能）/ `docs`（文档）/ `data`（数据产物）/ `test`（测试）/ `chore`（杂项）。
- **`scope`**：受影响的模块，如 `tasks`、`facilities`、`auth`；跨模块可省略。
- **摘要**：一句话说清改了什么，不超过 50 字，句末不加句号。
- **正文**：按 `更新` / `优化` / `修复` 分节，**只写有内容的小节**；每节用短条目列举**变更本身**。必要时可另加 `数据` / `文档` / `测试` / `维护` 小节。

## 三、写作要求（重点）

提交信息是**给后来人查历史的变更记录**，不是给某个人看的汇报。因此：

1. **写"改了什么"，不写"为你做了什么"** —— 不出现"我"、"你"、"本轮"、"按要求"、"已为您"。
2. **只写结论，不写过程** —— 排查思路、试错、为什么难发现、调试命令都归开发日志与代码注释，不进提交信息。
3. **不写情绪与强调** —— 不用 🔴 / ⚠️ / "重大" / "终于" / "彻底" 这类措辞；严重性用事实表达（如"导致全部验证码邮件被拒收"）。
4. **可核对** —— 涉及数量、体积、比例时给出具体数字（`20.92 MB → 7.40 MB`），便于日后比对。
5. **一条提交一个主题** —— 数据与代码混合改动可拆 `data:` 与 `feat/fix:`；纯测试调整用 `test:`。

## 四、提交范围约定

- **`dist/` 是构建产物**：不手动提交，由完整构建与发布流程产出；
- **数据产物 `public/data/parsed/*.json`**（预解析表）入库，供页面运行；重新预处理或完整构建仍需本机原表及派生输入；
- **`docs/history/dev-logs/YYYY-MM/YYYY-MM-DD.md`** 在阶段收口时随代码提交；同一天的不同模块合并到同一份日报，不按单次改动新建日志。

## 五、构建前置与原表维护

完整数据再生成需要本机原表、派生输入与剧情资源，**这些都不入库**，新环境必须另行准备。

- 游戏配置默认位于项目同级 `Config_decrypted`，剧情在 `GAoNano_decrypted`，游戏源码在 `源码`；
  可用 `MYRZG_CONFIG_DIR` / `MYRZG_DIALOG_DIR` / `MYRZG_SOURCE_DIR` 或维护脚本参数指定。
- `scripts/parse/index.mjs` 若在 `raw/` 与兼容目录 `public/data/` 都找不到 `reward.json`，
  但已有 `parsed/items.json`，会跳过预处理并沿用已有产物。**这个检查只判断文件存在**，
  不证明产物齐全、版本一致或原表完整；沿用产物的前端构建与从原表重新生成数据**必须分别验收**。
- `node scripts/dev/sync-raw.mjs` 默认只预览；`--apply` 补缺，`--apply --replace` 才更新
  已有完整原表及 `hero/`、`pet/`、`equip/`、`task/` 兼容别名。副本提取表与
  `monsterTowerUsage.json` 等派生输入不会被覆盖。
- 源目录含无效 JSON 时预览会列出全部问题，实际同步默认拒绝；只有人工确认这些表可排除后
  才加 `--skip-invalid`。已有原表与源版本不同的组不会只补一个新版本别名，需先复核 `--replace` 计划。
- `mon.json` 使用完整游戏原表，`cirtDam` 字段与头像引用只在预处理内存中归一化，**不改写原文件**；
  `battle.json`、`room.json` 同样不能被任务专用裁剪表覆盖。
- `node scripts/dev/check-task-data.mjs` 默认只读检查；`--apply` 才补缺原表、剧情并写入索引与报告。
- Web 与 Android 构建均保留运行时数据和图片。旧 `clean_dist.bat` 的删除策略已停用，
  **禁止删除 `dist/data`、`dist/images` 后再同步 Android**。

## 六、文档同步

路由、数据流、组件协议、字体或长期约束变化时，按 [文档职责](../../PROJECT_INDEX.md) 更新对应权威文档；
其他文档只调整必要摘要或链接，不重复写入同一实现细节。**开发日志不能替代规范。**

## 七、本地提交与推送

- 提交前对照 `git status`（含未跟踪文件）与 `git diff` 核对实际范围，**保留用户已有改动**，不把历史改动算成本次完成；
- 本地提交与推送分开处理；推送前按改动范围完成验收；
- 历史改写、强推和冲突处理需先检查实际分支与变更，**不把覆盖本地或远程内容作为默认方案**；确需改写已发布历史时，先建备份分支或 `git bundle`，并核对改写前后内容一致。
