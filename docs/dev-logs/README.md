# 开发日志规范

开发记录统一按日汇总。同一天无论涉及多少模块、多少次修改，都只维护一份日报；废弃按单次修改、独立主题或时分秒新建日志的规则。

## 1. 目录与命名

```text
docs/dev-logs/
  README.md
  YYYY-MM/
    YYYY-MM-DD.md
```

日期按项目时区 `Asia/Shanghai`。当天首次产生需要记录的改动时创建日报，后续直接合并到对应模块，不追加流水账式时间小节。跨日继续开发只记录当天新增结果，引用上一天的日报，不复制前文。发布说明可从日报汇总，但不另建一套重复的任务日志。

## 2. 日报模板

```markdown
# YYYY-MM-DD 开发汇总

## UI 与交互
- 用户可感知的变化、受影响页面和关键实现文件。

## 数据与解析
- 原表来源、字段规则、派生产物和数据更新注意事项。

## Bug 修复
- 问题现象、已确认根因、修复结果及必要回归场景。

## 重构与维护
- 公共能力调整、维护脚本、依赖或文档治理。

## 验证
- 实际执行的命令与结果；未执行项及原因必须明确。

## 发布与回退
- 是否需要完整构建、CDN 素材同步、热更包或 APK。
- 涉及删除/覆盖时记录备份位置及恢复方式。

## 未完成事项
- 明确尚未解决的问题；没有则写“无”。

## 文档同步
- 已更新的权威文档；未同步项及原因。
```

无改动的模块可省略。记录最终有效实现与重要取舍，不保留反复尝试、逐条聊天回应、重复构建输出或每次像素微调。不要把“准备执行”写成“验证通过”。

## 3. 记录与收口

- 需要记录：逻辑、数据规则、组件行为、架构、构建发布链或维护脚本的实质变化。
- 可不记录：只读分析、答疑、没有文件变化，或纯错别字修改。
- 阶段完成、提交或发布前集中整理日报；无需每次保存文件后写日志。
- 对照当前 `git status`（含未跟踪文件）和 `git diff` 核对实际范围，保留用户已有改动，不把别人的历史改动算成本次完成。
- 路由、数据流、组件协议、字体或长期约束变化时，按 [文档职责](../README.md) 更新对应权威文档；其他文档只调整必要摘要或链接，不重复写入同一实现细节。日报不能替代规范。
- 同一天的回滚记在同一日报，写明撤回的行为与复验结果。

## 4. 历史日志治理

2026-09-07 经用户授权，旧碎片日志先备份到项目外再清理；备份位置、校验与恢复说明记录在当天日报中。旧记录可从备份恢复，但不再保留于日常规范入口。清理不改变代码，也不代表旧日志中的结论仍适用于当前实现。

维护工具 `node scripts/dev/archive-legacy-logs.mjs` 默认仅预览；只有用户授权清理后才加 `--apply`。脚本将原文及 SHA-256 清单备份至项目同级 `backups/dev-logs/<时间>/`，逐一验证后仅删除已入清单的旧 Markdown，不删除本规范或标准日报，也不递归清除其他类型的文件。

以后确需导入旧记录时：先以文件名中的日期分组，对 Markdown 标题分段并保留来源文件名；将结论归入上述模块，去重后生成 `YYYY-MM/YYYY-MM-DD.md`。不同内容的同名标题不能直接覆盖。导入先预览清单与数量，复核日期、缺失内容和来源对应关系后才写入；已有日报采用增量合并，禁止整篇覆盖。删除原文件前必须验证外部备份可读且数量、大小及 SHA-256 一致。

按年月目录浏览、全文搜索模块关键词即可，不维护逐份日志索引或日志数量清单。
