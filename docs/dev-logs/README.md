# 开发记录与变更日志规范（Dev Logs）

本文档目录用于记录可交付的开发批次，不要求每次对话、每个小修正各建一份文件。历史日志按日期集中存放在 `archive/YYYY-MM-DD/`，目录结构本身就是归档入口，不再维护手工索引表。

## 1. 命名与存放

日志文件名统一为：

```text
YYYY-MM-DD_任务主题.md
```

日志直接写入当天目录 `docs/dev-logs/archive/YYYY-MM-DD/`。当天目录不存在时先创建。同一天、同一功能或同一用户目标下的连续修改必须复用同一份日志，后续调整追加到“批次变更”中；只有切换到独立功能、架构决策或发布批次时才新建文件。

旧日志保留原有带时间的文件名，不做批量重命名。

## 2. 批次模板

所有 dev-log 严格套用以下模板：

```markdown
# {任务标题}
> 开始日期：{YYYY-MM-DD}
> 最后更新：{ISO时间戳}
> 任务范围：{连续用户目标或功能主题}

## 修改范围
- 改动源码文件列表
- 构建/预处理产出物变更（如有）

## 批次变更
### {HH:mm} {阶段标题}
- 本阶段的核心逻辑或 UI 改动
- 后续同主题调整继续追加，不新建日志

## 验证与测试
执行过的验证（build / Playwright / 内容比对等）与结果；无则填「无」

## 遗留问题 / 未完成点
本次未解决的坑、待处理项，无则填「无」

## 发布影响提示
是否需要重新打热更包 / 上传 CDN / 是否影响旧包回退；无则填「无」

## 文档同步动作
- ✅ / ☐ 标记每个受影响文档是否完成更新
```

## 3. 触发与收口规则

- 需要写 dev-log：逻辑修改、预处理脚本改动、页面或组件成组变更、架构或数据流变更、数据产物变更。
- 允许先改后记：连续调试期间不要求每次修改都同步写日志；在阶段完成、准备提交、准备发布或切换到另一功能前统一收口。
- 合并原则：同一天、同一页面/功能、同一问题链路的修改写入同一份日志；用户对上一版效果的连续反馈属于同一批次。
- 新建原则：只有功能主题明显切换、产生独立架构决策、需要单独回滚，或跨日期继续开发时才新建日志。
- 跳过日志：只读排查、答疑、未产生文件变更、仅改注释/错别字/单行视觉微调，以及仅调整文档规范本身。
- 权威文档仍即时维护：如果改动改变了路由、架构、数据流、组件规范或长期约束，必须更新 `SPEC.md`、`ARCHITECTURE.md` 或 `UI_COMPONENT_LIBRARY.md`，不能只写 dev-log。
- 收口时通过 `git status`（含未跟踪文件）和 `git diff` 汇总实际改动，避免依赖对话记忆。

## 4. 归档查找

- 不再创建根索引或日期目录 `README.md`，也不维护日志数量。
- 通过 `archive/YYYY-MM-DD/` 按日期浏览，通过日志文件名按功能定位。
- 需要检索具体改动时，直接在 `docs/dev-logs/archive/` 全文搜索关键词。
- 日志文件名必须保持任务主题清晰，避免使用“调整”“修复问题”等无法检索的宽泛名称。

## 5. 回滚与归档

1. 回滚历史改动时，在当前批次日志写明被回滚的旧日志文件名，以及回滚后的构建和差异校验结果；仅当回滚本身是独立任务时才新建日志。
2. 日志创建后直接放入当天目录，不设“超过 30 份”或“跨月”阈值。
3. 移动或追加日志时不需要同步任何索引，只需保证文件位于与日期一致的目录中。

## 6. diff 自检

阶段完成、提交或发布前，读取本批次的 `git status`（含未跟踪）与 `git diff`：

1. 根据变更文件，对照 `docs/SPEC.md` 的文档维护约定，判断应更新哪些文档。
2. 检查对应文档是否真实出现在本次变更中。
3. 若未更新，应在收口时补写，或在批次日志的“文档同步动作”中明确标记。
