# 2026-10-07 开发汇总

## 任务图鉴：剧情搜索命中后自动定位

### 需求

任务页支持按剧情原文搜索（2026-10-06 已做）。但搜到之后，用户点开任务还得自己翻步骤、
找剧情、再往下滚 —— 等于把搜索的价值又还回去了。本次做到**点开即见**：
自动展开命中所在的步骤与该段剧情，并把那句话滚进视野（不做高亮）。

### 索引改为可定位

原索引是「每任务一段全文」，只能回答"这个任务命中了吗"，无法回答"命中在哪一步、
哪段剧情、第几行"，因此没法定位。

改为按 `步骤下标:剧情下标` 分块、块内保留**行数组**（`form: per-dialog-lines`）。
该 key 与 `TasksView` 的 `dialogOpen` 键一致，可直接用来展开对应剧情。

**实测这个形状与一坨文本的压缩后体积几乎相同**（brotli 0.58 MB，差 < 1%）：
块边界与换行本来就存在，拆成数组只是把它显式化，没有引入额外冗余。
产物 raw 2211 KB（1510 个剧情块 / 29182 行）。

### 行文本必须与页面渲染同源（原本不一致）

原先索引自己写了一套"只剥 `[show]/[l]/[cm]`"的清洗，而页面用的是
`cleanDialogueLine` —— 后者还会把 `{myName}` / `主角` 换成「小工匠」、
`{callNameN}` 换成「他（她）」。于是：

- 用户**看到的是**「小工匠，你醒了。」，搜「小工匠」却搜不到（索引里是 `{myName}`）；
- 就算搜到了，索引行与页面渲染行也对不上，无法定位。

改为复用 `cleanDialogueLine`。**索引里的每一行就是页面上那一行的文本。**

另外索引产出的条目粒度也改为**逐条镜像页面渲染**：页面把 `option` 合成**一条**
条目（所有选项收在一起），索引一开始却把每个选项各推一行，导致含选项的剧情
行号错位、滚动落到错误的行。

### 定位实现里踩到的三个坑（都会重复踩）

1. **滚动偏移不能用 `offsetTop` 相减**。`offsetTop` 相对 `offsetParent`，
   而命中行与 `#taskModalScroll` 中间隔着 `.step-accordion` / `.dialog-lines`
   等定位元素，相减得到的值偏出可视区（实测滚到 649、命中行却在 1026）。
   必须用 `getBoundingClientRect()` 相减 —— 与 `utils/scrollTarget` 的
   `alignElementInScrollTarget` 同一算法。
2. **必须等布局稳定再滚**。剧情展开后内容会**二次增长**：实测
   `scrollHeight` 从 1377 涨到 2191（先展开步骤，随后剧情正文把高度撑开）。
   在涨的过程中滚，算出的目标位置在布局稳定后已经不对。
   现在逐帧等到高度连续两帧不变再滚。
3. **`ensureDialogSearch` 必须返回在途 Promise**。原写法是"已在加载中就 `return`"，
   对"别重复请求"够用，但调用方 `await` 到的是 `undefined`，紧接着读命中仍是空。
   冷链接（`?task=...&q=...`）正好命中这个时序：watch 先发起加载、
   `openDetail` 随后调用被早退挡住 → 详情打开了但**没有定位**。

### 顺带修掉两个既有缺陷

- **`?q=` 从 URL 进不来**：`searchQuery` 只在 setup 里读一次，而本站是 hash 路由、
   站内跳转不重建组件 → 分享出去的搜索链接对方点开看不到结果。
  新增 `watch(() => route.query.q)` 做单向「URL → 状态」同步。
- **`watch(searchQuery)` 没有 `immediate`**：搜索词来自 URL 时初始化就已有值、
   不触发 change，索引永远不加载。补 `immediate: true`。

### 验证

| 项 | 结果 |
| --- | --- |
| 索引行 vs 渲染条目 | 1510 个剧情块**逐一对应**（单测锁住） |
| 边界用例 | 「小工匠」（称呼）/「弟子」（选项）/「契约」（普通）均 `inView: true` |
| 冷链接 `?task&q` | 自动展开并定位，`inView: true` |
| 正常浏览（无搜索） | 列表点击、`?task=` 冷链接均**不跳**（`scrollTop: 0`） |
| 单测 | 277 / 0 |
| `app-shell` UI 回归 | 31 passed |
| `npm run verify` | 全部通过 |

> 测试方法上又踩了一次"单次运行 / 同会话状态"的坑：早期用同一个 page 连续
> 导航去测"不搜索时不该跳"，读到 649 误判成乱跳 —— 实际是上一轮搜索的残留状态。
> 改用独立 `browser.newContext()` 后结果为 0。**测导航行为要给干净的上下文。**

## 安全加固一：响应头（CSP / HSTS / X-Frame-Options）

### 做了什么

`public/_headers` 新增全站（`/*`）安全头：

```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
  img-src 'self' data: blob:; media-src 'self'; font-src 'self'; connect-src 'self';
  frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), microphone=(), camera=(), payment=()
```

### 每条指令为什么是这个值（都对着本项目实际写法核过）

| 指令 | 值 | 依据 |
| --- | --- | --- |
| `script-src` | `'self'`（**不带 unsafe-inline**） | 这是 CSP 的核心价值。本站扛得住：`index.html` 与构建产物里**内联 `<script>` 0 个**，`onclick=` 等内联事件处理器**全仓 0 处** |
| `style-src` | `'self' 'unsafe-inline'` | Vue 的 `:style` 绑定会写成内联 style，**全仓 141 处**（招募坐标、地图节点、吉祥物、营地研究树）。不放开会让动态定位全废 |
| `img-src` | `'self' data: blob:` | `data:` = 点选验证码的 32 张 base64 蛋图（内联进 SVG `<image href>`）；`blob:` = 招募页 Spine 贴图（`URL.createObjectURL`） |
| `media-src` | `'self'` | 招募页 BGM 用 `new Audio(...)` |
| `frame-ancestors` | `'none'` | 防第三方 iframe 嵌套（`X-Frame-Options` 的现代写法，两个都写兼容老浏览器） |

### 自测工具（关键交付）

CSP 的误伤特点是**不报错、只静默失效**（图不显示、音不播、样式错位），
所以"配好了"不能靠肉眼看。新增 `scripts/dev/check-csp.mjs`（`npm run csp:check`）：

1. 从 `public/_headers` **解析出真实 CSP**（不另抄一份，避免"测的和上的不是同一个值"）；
2. 起本地静态服务托管 `dist/`；
3. 用 Playwright **给每个响应注入该 CSP**（等价于 Pages 套 `_headers`）；
4. 监听 `securitypolicyviolation` + 控制台，收集违规；
5. 走 8 个关键页 + 注册页人机验证，逐页截图。

**实测结果：9 个场景全部零违规**（含 8 张 `data:` 蛋图确实渲染出来）。
截图在 `scratch/csp-shots/`。

### 这个脚本自身踩的三个坑（都会重复踩）

1. **第一版是"空转"**：只点了「含『登录』字样的按钮」，而顶栏账号入口是
   `<button title="账号">`（文案里没有"登录"）→ 什么都没测到却报了 ✅。
   现在**断言蛋图数量 > 0**，测不到就判失败，不给假结论。
2. **注册页的邮箱框 placeholder 是「用来收验证码，也是以后的登录账号」**——
   里面**没有"邮箱"二字**。用 `/邮箱/` 宽匹配会命中登录页那个「注册时用的邮箱」，
   于是注册表单邮箱始终为空、被「请填邮箱」挡下，蛋图永远出不来。
3. **静态服务没有 `/api`** → 人机验证弹窗显示「无法连接账号服务器」→ 蛋图不渲染。
   现在就地用项目自己的 `buildCaptcha()` 出一道真题并 mock 该接口
   （**只 mock 取题，不 mock 提交**）。

> ⚠️ **开发环境不受 `_headers` 影响**（Vite 不读它），本地 `npm run dev` 看不到 CSP 行为。
> ⚠️ **Android 原生壳也不受它影响**（加载 `https://localhost` 的包内文件）——
> 这是"原生端没有 CSP 保护"，不是配置错误，如实记录。

## 安全加固二：密码盐改为每用户独立随机（对齐主流）

### 改动

原先 `salt = HMAC(SALT_SECRET, 'salt:' + 邮箱)` **派生**；现在**注册时客户端
`crypto.getRandomValues` 随机生成 32 字节**（64 位小写 hex），随注册请求提交，
服务端校验形状后原样存进 `users.pw_salt`。

### 为什么改

原先的派生盐满足"每人不同"但**不是随机**，偏离了 bcrypt / Argon2 / scrypt
这些主流密码哈希的通行做法（它们都是每条记录一次 CSPRNG）。

**关键转折点**：盐后来**必须入库**了（为了支持换邮箱 —— 现算会与注册时不同，
用户换完邮箱再也登不上，见方案 §4.2.1）。**一旦盐进了数据库，派生盐相对随机盐
就只剩缺点**：

| 攻击者拿到 | 随机盐 | 派生盐 |
| --- | --- | --- |
| 只有 D1 备份 | 攻不动 | 攻不动 |
| D1 备份 + `SALT_SECRET` | 仍需逐用户爆破 | **可自己算出所有盐 → 预计算可行** |

### 性能：无影响（甚至更快）

- 随机盐 `crypto.getRandomValues` ≈ 0.001ms，比一次 HMAC 还便宜；
- 只在**注册那一次**执行，登录直接从库里读 `pw_salt`；
- **真正的开销 PBKDF2 60 万轮完全没动**。

### 协议本身没变

盐仍是 **64 位小写 hex、客户端当 UTF-8 字符串用**（不做 hex 解码），
所以 `tests/ui/password-kdf.spec.js` 的跨端比对依然有效。

### 未注册邮箱返回"占位盐"

`HMAC(SALT_SECRET, 'placeholder:' + 邮箱)`，确定性。

⚠️ **这不是为了防枚举**（用户明确决定不做防枚举），而是**流程可用性**：
登录页提交前要先取盐，若对未注册邮箱直接报错，用户会在还没点登录时
就看到一个"邮箱不存在"式的错误。返回形状正常的占位盐，让流程走到服务端比对、
统一返回「邮箱或密码不对」，与主流站点体验一致。

它对同一邮箱**稳定**（不会两次请求返回不同值），所以不会因为"响应随机"
变成新的枚举口子 —— **这是副作用，不是目的**。

### 测试改动

- `auth-crypto.test.mjs`：改用 `generatePasswordSalt` / `placeholderPasswordSalt`；
  新增 5 条（随机盐 300 次不重复、形状、占位盐稳定性、随机盐不受 SALT_SECRET 影响等）；
- **所有注册调用点都要传 `salt`**，且**必须用随机盐、不能用 `/api/auth/salt` 的占位盐**
  （用占位盐会注册成功但**永远登不上**）。已改：
  `tests/helpers/accountApi.mjs`、`tests/api/auth-flow.mjs`、`tests/api/comments-auth.mjs`；
- `auth-flow.mjs` 新增两条断言：**随机盐 ≠ 占位盐**、**盐形状不对 → 400**。

### 安全加固的验证

| 项 | 结果 |
| --- | --- |
| 单测 | **280 / 0** |
| 端到端 `auth-flow` | **103 / 0**（含注册→存盐→登录全链路） |
| 端到端 `comments-auth` | **42 / 0** |
| UI `account-modal`（真表单注册） | **19 passed** |
| CSP 自测（9 场景） | **零违规** |
| `npm run verify` | 全部通过 |

> 端到端跑的是**真实流程**：注册时客户端随机生成盐 → 服务端存 → 登录时取回同一个盐
> → 派生出同一个 verifier。这是随机盐改动的**唯一可靠证据**，比读代码强。

### 安全加固未做

- **TOTP 二次验证**：全仓无实现，属独立功能，需要单独排期；
- **Argon2id**：Cloudflare Workers 不支持（`node:crypto` 明确排除 `argon2`，
  且 CPU 限流器无法中断密码学循环，故对 PBKDF2 直接入口封顶 10 万轮）。
  本项目把 KDF 放在**用户设备**上跑（PBKDF2 60 万轮 = OWASP 推荐值），
  而设备上的 `crypto.subtle` **同样只有 PBKDF2** —— 这是两端受限下的交集，不是偷懒。
- **防枚举**：用户明确决定不做。

## 后台权限体系：超管 / 管理员 + 审计 + 页面筛选

### 需求来源

原后台用**环境变量令牌**（`ADMIN_TOKEN`）：前端手输令牌存 `localStorage`，
请求带 `x-admin-token`。用户提出三点：

1. 令牌**怕泄露**（它永不过期、明文存 localStorage，泄露即长期有效）；
2. 希望**在页面上授权管理员**，而不是共享一个令牌；
3. 管理员**不该看到自己没有的权限设置**。

### 改动

| # | 内容 |
| --- | --- |
| 1 | `users` 加 `role` 列：`0` 普通 / `1` 管理员 / `2` 超管 |
| 2 | **删除令牌通路**，改为看会话账号的 `role`（`adminSession`） |
| 3 | 新增 `PATCH /api/admin/users/role`（**仅超管**，且不能产生超管） |
| 4 | 用户页加**角色列** + 「设为/撤销管理员」按钮（**仅超管可见**） |
| 5 | 新增 `admin_audit` 表 + `GET /api/admin/audit`（**仅超管**可读） |
| 6 | 补 3 处确认框（评论隐藏/放行/打回待审） |
| 7 | `pruneExpiredSessions`：登录时顺手清理过期会话 |
| 8 | 评论列表加 `pageKind` 筛选（横排按钮，非下拉） |
| 9 | `CLOUD_URL` 改为「默认值 + `VITE_CLOUD_URL` 可注入」 |

### 🔴 层级规则（本方案最要紧的部分）

```
          目标 普通0   目标 管理员1   目标 超管2
超管2       ✅           ✅            ❌
管理员1     ✅           ❌            ❌
```

没有这条，**管理员可以封禁甚至彻底删除超管** —— 而"彻底删除"不可恢复。
另加：**谁都不能操作自己**（防手滑自锁，超管自封等于永久失去后台）。

**超管不能通过接口产生**（`role=2` 被服务端拒绝）：避免"你给了某人超管、
他把你降级"的内斗。转移超管身份只能改数据库。

### 为什么敢删令牌通路

用户确认"能直接改数据库"就是后路。紧急恢复 SQL 写在迁移文件末尾：

```sql
UPDATE users SET role = 2, status = 1 WHERE email = '你的邮箱';
```

### 穷举矩阵测试（关键交付）

`tests/api/admin-roles.mjs`（`44/0`）把 `(操作者角色 × 目标角色 × 操作)`
**所有组合**跑一遍。为什么必须穷举：层级漏洞的形态是"**漏了一条分支**"，
代码看起来是对的 —— 靠"小心点写"防不住。

它守的不变量：
1. 只能操作角色**严格低于**自己的；
2. 谁都不能操作自己；
3. **只有超管**能设/撤管理员；
4. 接口**不能造出超管**；
5. 非管理员**所有管理接口**一律 401（不只 stats）；
6. 被拒绝的越权操作**不写审计**（没发生的事不该记）。

### 过程中查出的两个真 bug

1. **`canModerate` 量纲不一致**（界面在骗人）：管理端列表的 `u.id` 是**内部自增 id**，
   而 `currentUser.id` 是**对外编号**（`toPublicUser` 把 `public_no` 映射成 `id`）。
   两者直接比较永远不等 → "不能操作自己"在**界面上完全失效**，超管会看到自己那行
   也有「封禁/彻底删除」（点了才被服务端 403）。后端是稳的，但界面误导。
   已修，并加了 UI 回归（`🔴 自己那一行不给操作按钮`）。
2. **`link-integrity` 的嵌套路由清单写死**（`['', '/comments', '/users']`）：
   新增 `/admin/audit` 后它漏了，导致"路由不存在"**误报**。改为从源码推导
   （先定位 `children: [`，再向前找最近的顶层 `path`）。

### 测试改动

- 新增 `tests/api/admin-roles.mjs`（44 断言）；
- `auth-flow.mjs`：管理端改为**注入超管会话**（原 `x-admin-token` 已不存在），
  并新增"普通登录用户也进不去"的断言（`有会话≠有权限`，比"未登录 401"更易漏）；
- `tests/ui/admin.spec.js`：改为**注入 `myrzg:auth` 会话**，新增
  「角色按钮只有超管看得见」「超管能设管理员并记入审计」「按页面类型筛选」
  「自己那行不给操作」四条；
- **踩坑**：`goto('/')` 后再 `goto('/#/admin')` 只是**同文档 hash 变化**，
  不会重新加载 → 注入的会话永远读不到（表现为"管理员却进不去"）。
  改用 `addInitScript`（每次导航、页面脚本之前执行）。

### 额度实测（顺带纠正两处我先前说错的数）

用 `EXPLAIN QUERY PLAN` 在 1k 用户 / 5k 评论的合成库上量：

| 场景 | 5k 评论时 | 是否随总量增长 |
| --- | --- | --- |
| **普通用户**读讨论区（50 条） | **51 行** | ❌ 不增长（走 `idx_comments_page`） |
| **管理员**打开概览页 | ~17,000 行 | ✅ 线性增长（`COUNT(*)` 全表扫） |
| 管理员打开评论列表 | ~5,000 行 | ✅ 线性增长 |

**纠正**：先前说"`/api/admin/users` 每请求读 51 行"（把 `LIMIT` 上限当成实际开销）
与"评论列表约 100 行"（实际是全表扫）**都不准确**。

**结论**：用户侧读评论**不随数据量增长**（索引设计正确）；唯一会增长的是
**后台概览页**，临界点约在"10 万条评论"。现在库里共 13 行，**离该问题很远**，
故只记为待办、不动代码。

## 评论定位：不在首屏时显示定位卡片

### 问题

「谁回复了我 / 我的评论」的「去看看」会跳到 `#/discussions?c=<id>` 并滚到那一条。
但讨论区只加载第一页，那条回复可能已是几百条之前 —— 于是
`scrollToComment` 找不到目标就 `return`，**静默什么都不做**：页面跳过来了，
没定位、也没提示，用户以为坏了。

### 三种解法与取舍

| 做法 | 请求数 | 问题 |
| --- | --- | --- |
| 逐页往回翻 | 随"多老"增长（最坏几十次） | 越老越慢 |
| **只显示那两条**（采用） | **恒定 1 次** | — |
| 限制讨论区历史条数 | 省不了首屏额度 | 还丢掉回看功能 |

第三条专门核过：讨论区**一页 20 条**，截断省不掉首屏那 20 行（必然成本），
只省"用户主动翻历史"的部分 —— 而那部分一天 500 万行额度够翻 25 万页。
**所以不做截断。**

### 实现

- 新增 `GET /api/comments/context?page=<key>&id=<id>`：返回那条评论 + 其父评论
  + `inFirstPage`。**恒定 1 次请求**。
- 🔴 **越权防线**：查询同时限定 `page_key` 与 `status = 1` —— 否则拿一个 id
  就能读到任意页面、或被隐藏的评论。条件不满足统一返回 `found: false`，
  **不区分"不存在"与"被隐藏"**（避免被拿来探测）。
- `CommentsPanel.scrollToComment` 改为**返回是否找到**；调用方据此决定是否取上下文。
- 前端在列表上方显示卡片（被回复的那条 + 回复本身）；找不到时给明确文案。

### 过程中修掉的三个 bug（全是"静默"型）

1. **`get is not defined`** —— 路由里用了 `handleAuthRoutes` 的局部变量 `get`，
   在 `onRequest` 作用域不存在 → 整个接口 500。端到端测试抓出来的。
2. **页大小两处各写一份** —— 服务端写死 `FIRST_PAGE_SIZE = 50`，
   而前端 `fetchComments` 默认 `limit = 20` → 第 21~50 条被误判成"在首页里"，
   不显示卡片，用户又回到"点了没反应"。已抽成共享常量 `COMMENT_PAGE_SIZE`。
3. **边界差一条** —— `OFFSET N` 取到的正是第 N+1 条（页外第一条），
   比较必须用**严格大于**；用 `>=` 会把它算进页内，症状是"只有第 21 条点不动"。

### 还有一个更隐蔽的（卡片被自己的滚动优化弄没了）

卡片最初放在 `.discussion-scroll` **内部**、列表上方。而首屏默认"滚到最新"，
于是卡片被顶出视野 —— **东西渲染了但看不见**，观感与修复前一样。
改成"出现时把容器滚到顶部"后又引发连锁：滚到顶部 80px 内会触发
「加载更早的历史」，于是**自动一页页往前翻**，翻到那条时卡片又消失
（正好是本文想避免的行为）。

**最终解法：把卡片放到滚动容器之外**（与下方发表区同理）——
不占滚动位置、也绝不触发加载。删除那段"滚到顶部"的 watcher。

### 测试

| 文件 | 覆盖 |
| --- | --- |
| `tests/api/comment-context.mjs`（21/0） | 带出父评论、隐藏取不到、跨页面取不到、非法入参 |
| `tests/api/comment-page-boundary.mjs`（8/0） | **页大小边界**：第 20 条在页内、第 21 条必须在页外（旧 bug 的误判区） |
| `account-modal.spec.js` | 「去看看」定位到不在首屏的评论时显示卡片，并断言卡片**真的在视口内** |

### 为什么这些 bug 都值得记一笔

三个都是**静默型**：不报错、日志干净，只是"某一段范围的点不动"或"东西在但看不见"。
共同点是**两个地方各有一份事实**（页大小）、或**两个机制互相干扰**（自动滚动 vs 卡片）。
端到端与边界测试是唯一能抓住它们的办法 —— 单看代码每一处都像是对的。

## 后台闸门居中、身份条精简、登录预取盐

### 1. 权限闸门按钮偏左（用户截图指出）

`.admin-gate-row` 是固定 `420px` 宽的盒子，而 flex 默认 `justify-content: flex-start`
→ 内容贴左。旧设计那里是**输入框**（占满 420px）所以看不出来；删掉令牌闸门后
只剩两个小按钮，就露出"标题居中、按钮偏左"的错位。

修法：加 `justify-content: center`（**保留**固定宽度，窄屏下仍不至于撑满）。
实测按钮组中心与容器中心偏移 **0px**。

### 2. 身份条只显示昵称（用户要求）

`CommentComposer` 的身份条原为「以 **昵称** 的身份发表」+ 下一行「编号 10000」。
用户要求去掉后者与编号。改动：

- 文案缩为**纯昵称**；
- 连带改样式：原来那套是"灰色小字 + 竖排"（配合长句子），单看一个灰名字
  会像占位符，改为**正文字号、正常颜色**，读起来就是"这条是你发的"；
- 删掉 `.comment-identity-no` 样式与 `phone/flow.mjs` 里断言旧文案的那条。

### 3. 手机端登录要等好几秒 —— 查清了原因，并省掉一次往返

**先排除一个误解**：60 万轮 PBKDF2 **没有被取消**（`PBKDF2_ITERS = 600000` 未变，
`git log` 对该文件只有账号体系那一次提交）。

**实测拆解**（本地 vs 生产）：

| 环节 | 本地 | 生产 |
| --- | --- | --- |
| PBKDF2 60 万轮 | **107 ms** | 同（跑在用户设备上） |
| 取盐往返 | 12 ms | **中位 1258 ms**（样本 4956/1355/713/1258/525） |
| 登录往返 | 30 ms | **约 1300 ms** |
| 合计 | **149 ms** | **约 2.4~3 秒** |

**结论：计算只占 0.1 秒，其余全是网络**。关键旁证：走边缘缓存的 `/api/recent`
稳定在 **311 ms**，而每次回源的 `/api/health` 中位 **5485 ms**（样本波动 358~6350ms）
—— 瓶颈是**回源往返**，不是带宽也不是 CPU。

**优化：预取密码盐**。登录原本是**两次串行往返**，改为在用户**离开邮箱输入框**时
就取回盐，点登录时只剩一次。

- 盐由公开接口返回、**不是秘密**，缓存它不降低安全性；
- 客户端 `saltCache` 存的是 **Promise**（并发调用共用同一次请求），用完即丢；
- **失败即清缓存**，下次用新鲜值。
  > 想过"失败时拿新盐重试一次"，但那是净亏：服务端对"密码错"与"盐过期"返回
  > **同一个 401**（刻意如此，防账号枚举），无法区分；而"密码错"远比"盐过期"
  > 常见，重试等于**让每次输错密码都多花一次往返**（1.3 秒）。清缓存零成本。

**实测效果**（本地）：登录期间发出的请求从 **2 个降到 1 个**（`/api/auth/salt`
不再出现在登录阶段），点登录到完成 **240 ms**。

> ⚠️ 移动端在**弱网/首次**仍会慢 —— 那部分省不掉（省的是"第二次往返"和"冷启动"）。
> 真正的改善幅度取决于你那条链路当时的状态。

### 测试

- `account-modal.spec.js` 新增「登录前预取密码盐」：**数请求次数**而不是量耗时
  （耗时受网络波动影响，不可靠）—— 断言登录期间不再出现 `salt` 请求；
- `phone/flow.mjs` 的身份条断言改为"显示当前昵称"（原来断言的是被删掉的旧文案）。

## 评论「转待审」：补上回待办队列的入口

### 起因

盘点状态按钮时发现：评论页只有「放行 / 隐藏 / 彻底删除」，
**没有任何入口能把一条评论改回 `status = 0`（待审）**。
而后端 `adminPatch` 一直允许 `[0, 1, 2]`，文档也从未提过这个操作 ——
**不是被删掉的，是当初就没做**。

（另有一处佐证：前一轮给状态变更补确认框时，我给 `status = 0` 写了文案
却找不到调用点 —— 于是它成了**永远不会执行**的死代码。写过文案却没有入口，
比不写更糟：下次读到会以为功能存在。）

### 「待审」与「已隐藏」到底差在哪（逐处核对过）

结论：**对外完全等价**，全仓所有读路径一律只放行 `status = 1`：

| 判断处 | 条件 |
| --- | --- |
| 读评论列表 / 右栏 / 上下文接口 | `WHERE status = 1` |
| 父评论引用 | `LEFT JOIN ... AND p.status = 1` |

两者差别**只有两处**：

| 差别 | 待审(0) | 已隐藏(2) |
| --- | --- | --- |
| 作者在「我的评论」看到的标签 | 「待审核」 | 「已隐藏」 |
| **算不算进待办** | ✅ 计入 → 概览页 `pending > 0` 描红 | ❌ 不计入 |

所以「转待审」的语义是**挂起待定 + 放回待办队列**，不是改变可见性。
它的价值来自「待审」这个**队列**语义（概览页的"去处理 →"、待审筛选档、
作者看到的"待审核"标签，一整套 UI 早就建好了，只差放进去的入口）。

### 改动

- 评论操作列新增「转待审」，**仅当 `status !== 0` 时显示**
  （已经是待审的再显示"转待审"没有意义）；
- 操作列宽 `190px → 250px`（后台是电脑端专用，宽度不是约束）；
- 确认文案按**语义**区分，并顺手修正了「隐藏」那句不准确的话 ——
  原文写"隐藏后只有你能看到"，实际**作者自己也能看到**（显示为「已隐藏」）；
- 上一轮那段 `status = 0` 的死代码文案**现在是活的**。

### 三个状态各显示哪些按钮（实测）

| 状态 | 按钮 |
| --- | --- |
| 待审 | 放行 / 隐藏 / 彻底删除 |
| 已显示 | 隐藏 / **转待审** / 彻底删除 |
| 已隐藏 | 放行 / **转待审** / 彻底删除 |

### 测试

`admin.spec.js` 新增用例，验的是**双向**而不只是"按钮在"：

1. 已显示的评论能点「转待审」；
2. 转完**从「已显示」档消失**；
3. 在「待审」档里能找到它；
4. 🔴 **概览页的待处理计数真的 +1** —— 这是这个状态唯一的实际作用，
   不验它等于没验。

> ⚠️ 写这条时踩了个测试自身的坑：断言"它不在这一档了"原本写成
> `.admin-card` 不含文本，但**列表为空时 `.admin-card` 整个不存在**
> （页面渲染的是「没有匹配的评论。」），于是 `not.toContainText`
> 会因为"找不到元素"而失败 —— **行为是对的，测试在误报**。
> 改成**数行**（不该有任何一行含该标记）。

## 剧情搜索失败态：自动重试一次 + 文案说清怎么办

### 现象

任务页提示「剧情搜索暂时不可用（仍可按任务名与描述搜索）」，
第一反应是"是否需要去 CDN 刷缓存"。

### 排查结论：**不需要刷缓存，数据与边缘缓存都没问题**

实测（2026-10-07）：

| 检查 | 结果 |
| --- | --- |
| `dialog-search.json?v=<期望哈希>` | **200**，808 KB |
| 内容哈希是否匹配 | **匹配**（`6b740404…`） |
| `meta.form` | `per-dialog-lines`（**新格式**，正确） |
| 真浏览器搜索 | **正常出剧情命中行**，控制台无错误 |

**所以那是「那一次加载」的瞬时失败**，不是持续故障。成因是 CDN 侧新旧副本交替：
内容刚更新时，带**旧哈希**的 URL 可能仍命中旧副本 → 哈希校验失败 → 抛错。
新哈希 URL 从来不受影响 —— 这正是内容寻址的设计目的。

> 顺带核实：`?v=<新哈希>` 与 `?v=<随机串>` 返回**完全一致**，
> 说明边缘并不忽略查询串，不存在"要手动刷缓存"这回事。

### 改动

1. **失败自动重试一次**（间隔 600ms）。`fetchWithFallback` 失败时会清掉缓存条目，
   所以第二次是**真的重新发请求**；只重试一次，避免真挂时白烧用户流量与 CDN 额度。
   重试成功用户**什么都看不到** —— 多数瞬时抖动就此消失。
2. **文案改成能指导操作**：
   `剧情搜索暂时不可用` → `剧情搜索加载失败，刷新页面重试`。
   "暂时"听起来像站点出故障，而实际上刷新一下多半就好，但原文没有"刷新"二字。
3. **失败时 `dialogSearch` 保持 `null` 而不是 `{}`**：
   `{}` 是真值，会让下次调用在入口直接返回 —— 于是"重新搜索"也拿不到数据，
   只有刷新整页才行。

> 曾短暂加过「重试」按钮，按要求去掉，只改文案。

### 验证

用 Playwright **拦截 `dialog-search.json` 让它必然失败**，实测：

| 项 | 结果 |
| --- | --- |
| 拦截次数（= 请求次数） | **2**（证明自动重试真的发生） |
| 提示文案 | 「剧情搜索加载失败，刷新页面重试（仍可按任务名与描述搜索）」 |
| 旧文案是否残留 | **否** |
| 降级是否可用 | 仍能按任务名搜出 3 张任务卡 ✅ |

## 任务页黑名单漏出：章节序号没有映射成地区名

### 现象（用户报告）

任务页搜「大书院」时，**第五章**的任务照样出现 —— 而第五章 = **霜烬平原**，
属于按黑名单隐藏的地区。搜**剧情正文**时尤其明显（对话里直接出现「黑森林」这类词）。

### 根因：黑名单认地区名，任务带的是章节序号

```js
isBlacklisted({ id, name, desc, tip: item.typeLabel, label: item.subLabel })
//                                            ↑ "主线"      ↑ "第五章"
```

黑名单里存的是**地区名**（`黑森林` / `霜烬平原`），而任务上的 `subLabel`
对**主线**是**章节序号**（`第五章`）、对**委托/支线**才是地区名。
**同一地区两种写法**，主线那一路字面永远匹配不上 → **整章漏出 42 条**。

### 数据核实（不是推测）

| 事实 | 数据 |
| --- | --- |
| 第四章 ≡ 黑森林 | 主线四章任务里 **12/14** 带 `c4_` 前缀 |
| 第五章 ≡ 霜烬平原 | **9/11** |
| 漏出总量 | **42 条**（第四/五章） |
| `subLabel` 写法分布 | 主线用「第 N 章」，委托用「霜烬平原」 |

### 改动

1. **新增 `resolveRegionName(subLabel)`**（`gameMappings.js`）：同时接受
   章节序号与地区名两种写法，统一成地区名；认不出返回空串（不误判）。
2. **`CHAPTER_TO_MAP` 从 `furnitureData.js` 提到 `gameMappings.js`**（`MAP_NAMES` 旁）。
   该文件开头就写着「全站统一从这里取映射，禁止在页面里各自写死」——
   而任务页也要用它，两处各存一份必然走散。
3. **任务页黑名单判定补上地区名**，用 `place` 字段传入。

> 🔴 两个**踩过的坑**（都属"看着对、其实没生效"）：
> ① 起初自造了一个 `region` 字段 —— 但 `isBlacklisted` **不认识它**，会被静默忽略。
>    必须用它的 `parts` 拼装清单里**确实会读**的字段（`place` 正合适）。
> ② `place` 必须传**数组**：blacklist 里写的是 `...item.place`，
>    直接给字符串会被按字符展开（`"霜烬平原"` → `"霜 烬 平 原"`），反而匹配不上。

### 效果（实测）

| | 修复前 | 修复后 |
| --- | --- | --- |
| 隐藏任务数 | 29 | **71**（+42） |
| 新增隐藏的章节 | — | **全部第四/五章**（23 + 19） |
| 误伤其他章节 | — | **0 条** |
| 搜「大书院」命中第四/五章 | 有 | **0 条** ✅ |
| 搜「黑森林」命中隐藏地区 | 有 | **0 条** ✅ |

### 测试

新增 `tests/unit/task-blacklist.test.mjs`（4 条）：映射链路、隐藏地区主线被挡住、
本次改动不波及非隐藏章节、`CHAPTER_TO_MAP` 与 `MAP_NAMES` 一致。

> ⚠️ 写测试时**自己也误判过一次**：断言起初写成"序章/一~三章一条都不该被隐藏"，
> 结果红了。查下去发现那两条（序章「前往驿站」）是**旧逻辑本来就隐藏的** ——
> 它们的 `desc` 写着"你救助了一名来自**黑森林**的信使…"，而黑名单是**按名字模糊匹配**、
> `desc` 也在匹配范围内。那是**既有设计**，不在本次改动范围内；
> 拿它当断言等于**要求顺手改掉别的功能**。
> 断言改为只针对 `新增隐藏`（`after && !before`）那部分。
