### 事件图鉴：隐藏地区（黑森林 / 霜烬平原）漏出

**现象**：事件图鉴「全部」下能看到只属于隐藏地区的条目 —— 随机事件的「逃跑的蕈人」（c4）、
「攀登雪山」（c5），以及探索区域的 c4/c5 全部条目。筛选按钮已经隐藏了这两个地区，
**卡片却还在**，按钮与内容口径不一致。

**根因**：事件条目的地区信息**不在 `name` 里**，而在数组字段：

| 类型 | 地区字段 |
| --- | --- |
| 随机事件 | `maps`（`c4_map`）+ `mapNames`（`黑森林`，数组） |
| 探索区域 | `mapKey`（`c4_map`）+ `mapName`（`黑森林`，单值） |

而 `isBlacklisted` **只读固定一组字段名**（`name`/`desc`/`tip`/`source`/`label`/`keywords`
与数组型 `category`/`categories`/`place`/`mark`），`maps` / `mapKey` 会被**静默忽略**。
页面当时只传 `{ id, name }`，而「废弃的宝箱」这类事件名不含地区名 → 匹配不到 →
筛选按钮靠 `isBlacklisted(label)` 隐藏了，列表这条通路却没有。

**修复**：

- `utils/eventData.js` 新增 `eventRegionLabels` / `isHiddenRegionEvent` / `visibleEventMapNames`
  三个纯函数（**唯一实现**，页面与单测共用一份）。
- `EventsView.vue` 的加载过滤改用 `isHiddenRegionEvent`；详情「出现地图」标签改用
  `visibleEventMapNames`，不再列出隐藏地区。

**判据选择**：「所属地区**全部**命中黑名单」才整条隐藏。只命中部分时保留 ——
跨地区事件（如「废弃的宝箱」c1~c5 都有）在可见地区也能遇到，按"提到即隐藏"会误伤。
这与 [DECISIONS.md](../../../context/DECISIONS.md) ADR 116「黑名单判据是条目归属，不是文本提到」一致。

**影响面**（实测）：

| --- | --- | --- | --- |
| 随机事件 | 20 | **18** | 2（`e_c4_1` / `e_c5_1`） |
| 探索区域 | 80 | **48** | 32（c4：16、c5：16） |

**回归**：新增 `tests/unit/event-blacklist.test.mjs`（4 条，守地区判据与"不依赖 name"）

### P1 缺陷：打开任意图鉴页都会全表扫评论（`idx_comments_page_id`）

**现象**：`GET /api/comments?page=<pageKey>` 对**一条评论都没有的页面**，
数据库要扫完整张 `status = 1` 索引。空页成本 = **全站评论数**。

**为什么是严重缺陷（与当前评论多少无关）**：成本是**页面数量 × 评论数量**的乘积。

| 环节 | 事实 |
| --- | --- |
| 前端 | `CommentsPanel` 挂在 **9 处**图鉴页（物品/角色/魔物/家具/任务/事件/副本/关卡/物品与怪物详情弹窗），且**挂载即请求**（`CommentsPanel.vue` 的 `if (props.pageKey) load()`） |
| 页面数 | 全站页面键 **千级**：物品 816 + 任务 315 + 家具 141 + 怪物 52 + 角色 34 + 魔物 32 + 事件 20 + … |
| 分布 | 绝大多数页面**零评论** |
| 计费 | D1 免费版读额度 5,000,000 行/天，**超限直接报错**（非限速）→ 讨论区全员挂掉 |

日消耗 ≈ 日浏览量 × 全站评论数。评论发布后即开始按乘积增长。

**根因**（两半叠加，缺一不可）：

1. **索引尾列与排序不匹配** —— 查询是 `WHERE page_key = ? AND status = 1 ORDER BY id DESC LIMIT 21`，
   而 `idx_comments_page(page_key, status, created_at DESC)` 的第三列是 `created_at`，
   无法用于满足 `ORDER BY id DESC`。
2. **规划器选择** —— 生产库与本地库都**从未跑过 ANALYZE**（`sqlite_stat1` 不存在）。
   缺统计信息时规划器选
   `SEARCH comments USING INDEX idx_comments_status_id (status=?)`，
   即沿 `(status, id DESC)` 从最大 id 往下**逐行扫、用 page_key 过滤**，凑够 21 条才停。
   零评论的页面**永远凑不够** → 走完整张索引。

**实测**（独立实验库 + 真实 `EXPLAIN QUERY PLAN`，30,000 条评论）：

| 查询 | 修复前 | 修复后 |
| --- | --- | --- |
| 打开热点页（有评论） | 33 行 | 21 行 |
| **打开空页（平铺）** | **27,000 行** | **0** |
| **打开空页（楼中楼）** | **27,000 行** | **0** |
| 展开回复串 | 33 行 | 21 行 |
| 定位页边界 | 27,000 行 | 18,000 行 |
| 站内讨论区最新 | 32 行 | 20 行 |
| 我的评论 / 后台分页 / 状态计数 / 7 日趋势 | — | **全部持平** |

**修复**：新增 `idx_comments_page_id ON comments(page_key, status, id DESC)`。
尾列 `id DESC` 与 `ORDER BY id DESC` 一致 → 可沿索引取够 `LIMIT` 即停，空页 0 行。

**为什么是新增而不是改掉旧索引**：`idx_comments_page` 的 `created_at` 正被概览
「7 日趋势」（`SELECT date(created_at,…) … WHERE created_at >= ?`）借道当**覆盖索引**
（带 skip-scan）。把它换成 `id` 会让那条查询退化成 `SCAN comments`（实测失去覆盖）。
新增使两条查询各走对的索引。

**⚠️ 实测记录的陷阱**：若全部评论集中在**同一个** `page_key` 上，`ANALYZE` 会让
`sqlite_stat1` 把一个前缀值记成"N 个不同值"，规划器据此**退回全表扫**
（实测：无 ANALYZE 0 行 / 有 ANALYZE 4,000 行）。生产库无 `sqlite_stat1`，走前者；
将来若要补跑 `ANALYZE`，需先复查 `tests/unit/comments-page-index.test.mjs` 的哨兵用例。

**改动**：

| 文件 | 动作 |
| --- | --- |
| `scripts/sql/2026-10-15-comments-page-id-index.sql` | 新增（第 12 步迁移，幂等，含自检 SQL） |
| `schema.sql` | 同步新增索引与说明（新建库直接带上） |
| `tests/unit/comments-page-index.test.mjs` | 新增（8 条守卫） |

**回归**：`tests/unit/comments-page-index.test.mjs` 8/8 通过。断言口径是
**实际扫描行数不随全站评论数增长**（而不是查计划文本 —— 那会变成脆弱的实现细节测试）。
全套单测 378/378 通过；迁移演练 67/67 通过；`npm run csp:check` 零违规。

### 事件图鉴：图槽品质框平铺成「6 个格子」

**现象**：事件卡片在图片未加载完时，一个图槽里显示 **3 列 × 2 行 = 6 个方格**，
像是"一个区域渲染了 6 个格子"的显示 bug（用户报告）。

**根因**：`EventsView.vue` 的图槽样式用了 `background:` **简写**给纸色底：

```css
/* ❌ 简写会把未列出的子属性重置为初始值 */
.events-page :deep(.ui-item-card__slot) { background: var(--paper-soft, #e9dcc3); }
```

CSS 简写规则：`background` 会**重置**所有未列出的 `background-*` 子属性。
于是 `UiItemCard.vue` 为品质框设的这两个声明被覆盖：

| 属性 | `UiItemCard.vue` 设定 | 被简写重置为 |
| --- | --- | --- |
| `background-size` | `100% 100%` | `auto` |
| `background-repeat` | `no-repeat` | `repeat` |

而该背景图是 **76×76 的单格**品质框（`ItemBagPanel/item_f_N.webp`），
图槽在事件页被放大成 16:9 大卡（实测 **246×138**）——
76×76 以 `auto` 尺寸 `repeat` 平铺，横向 3 个 × 纵向 2 个 = **正好 6 格**。

图片加载完成后 `<img>` 以 `object-fit: cover` 铺满图槽把背景遮住，所以只有"没加载出来"时可见。

**修复**：改回 `background-color`（只设颜色，不动其他子属性）。

**取证**（CDP 读 computed 值，修复前后对照）：

```
修复前： background-size: auto        background-repeat: repeat      → 平铺 6 格
修复后： background-size: 100% 100%   background-repeat: no-repeat    → 单格
```

**回归**：`tests/ui/events-blacklist.spec.js` 第 2 条断言 `background-size === '100% 100%'`
且 `background-repeat === 'no-repeat'`，防止简写再次覆盖。

> 这类缺陷**不能靠截图判断**（图片加载完就看不见了），也不能靠读源码"看起来对"
> —— 只能读 computed 值。判据写法与 [RISKS.md](../../../context/RISKS.md) 故障 24
> （滚动条样式「写了却没生效」）同源：**声明存在 ≠ 声明生效**。

### 任务图鉴：接取 NPC 显示「未知（cart_at_npc_glt）」

依据源码 `DailyTaskPanel.cs:244-249`（NPC 名与立绘成对显示）：


   本来就是"搭话台词"，那行是有意义的。

### NPC 查不到名字时省略该行（方案 A）

**问题**：45 处 NPC 显示「未知（内部 id）」，如 `未知（ke_sldsd_21）`、`未知（NPC031）`。

**查证（穷举，非推测）**：25 个 uid 在**任何表里都没有名字**

| 查证项 | 结果 |
| --- | --- |
| `room.npcList` 精确匹配 | 0/25 |
| 其所在房间（`yzdq_5`、`sldsd_6` …） | 在 `room.json` 里**不存在** |
| `npc.json` | 只命中 1 个（`worker_thanks`），该表**无 name 字段**（仅 `uid/icon/image/viewData`） |
| 全 raw 表扫 uid | 只在 `task.json` 出现；`room.json` 里仅作为 `npcMove` 动作参数（不在 `npcList`） |

**决策**：查不到就**不产出该行**，不显示内部 id。

依据源码 `TaskPanel.cs:385-386` —— 任务界面只显示 `stepName` + `stepDes`，
**步骤级没有 NPC 行**，所以省略与游戏一致。

**实现**：`npcText()` 改为「无名字返回 `null`」；`getTask.npc.name` 解析不出时置 `null`；
页面 `v-if="npcText(...)"` 不渲染。`line`（交互对话）**独立保留**。

**验收**（HEAD 与工作区逐条对比）：

```
移除「未知（内部 id）」：任务级 7 条 + 步骤级 38 条 = 45
误删真名：0
可读真名总数：861 → 1028
```

**踩到的坑**：验收脚本第一版把字符串 `"未知（xxx）"` 当成真名，得出「误伤 7 条」的假警报。
判据必须显式排除 `未知` 前缀（`isNoName`），不能只判断「非空」。

## 两处自我订正（结论报错了）

### 订正 1：`diary.json` 不属于任务图鉴

前面把 `diary.json` 的同步问题写在**任务图鉴**这一段里，是错的 —— 两者无关：

| 项 | 消费方 | 产物 |
| --- | --- | --- |
| 任务图鉴 | `taskParser.js` ← `tasks.mjs` | `parsed/tasks.json` |
| `diary.json` | `runtime-tables.mjs` 的 `PASSTHROUGH` | `parsed/diary.json`（**物品详情**的书籍/日记文本） |

`tasks.mjs` 与 `taskParser.js` 都不读 `diary.json`。该项已从任务图鉴段落移出，只留在 RISKS 25。

### 订正 2：`raw/diary.json` **不是**旧版本

原判断「源表 2026-07、副本 2026-09 → 副本可能落后」是**拿文件时间当依据**，未验证内容。

实际逐字比对（剔除全部空白与转义后）：

```
taskMain  字串数 源=112 raw=112  ✅ 完全一致
taskSub   字串数 源=  0 raw=  0  ✅
word      字串数 源=188 raw=188  ✅ 完全一致
book      字串数 源= 42 raw= 42  ✅ 完全一致
```

**源表与副本的可见文字完全相同**，差异只在换行表示：源表是裸 `\r\r\n`（这正是它不合法 JSON 的原因），
副本存成转义后的 `\n\t`。所以 `raw/diary.json` 是**同一内容的可用版本**，不是过期数据。

**当前无数据偏差**。真实风险只是**将来**：源表更新时同步不进去且无报错。

> 教训：**文件修改时间不是内容新旧的证据**。判断"数据是否过期"必须比对内容本身。
> 这与本日另外三处（注释当依据而不回源码）是同一类错误：**用间接信号代替直接验证**。
