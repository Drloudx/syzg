# 2026-10-04 开发汇总

> 主题一：**讨论区/评论发表区加聊天表情**（黄豆 emoji + 深渊之歌第1弹），
> 正文以 `[e:包:名]` token 与文字一起存进原来的纯文本列；
> 顺带修掉一个「表单里的 `UiButton` 其实是隐式 submit」的坑（点表情按钮会把表单提交掉）。
>
> 主题二（同日用户反馈后）：**发表区换成富文本输入**（表情直接显图，不再是 `[e:...]` 代号）、
> **发送方式默认 Enter**（可切 Ctrl+Enter，新增库组件 `UiSplitButton`）、选择器向右展开、

## UI 与交互

### 发表区：左下角表情入口 + 按显示字数计数

- `CommentComposer.vue` 底部一行改为 `[表情按钮] [0/200] …………… [发布 ⌄]`：
  表情按钮在最左（用户指定位置），字数计数器紧随其后，「发布」是组合按钮（见下）。
- 表情按钮**复用 `UiButton`**，方形尺寸由 `align-self: stretch` + `aspect-ratio: 1/1` 决定——
  不写死像素、自动等于这一行的高度（实测 28×28，与「发布」同高），改动「发布」字号/内边距时不会错位。
- **配色**：`variant` 从 `primary`（深原木）换成 **`secondary`（羊皮纸描边钮）**，
  描边与图标取 `--border-color`（**滚动条滑块同色**）——用户反馈原来的深色"太沉"。
- **图标**：`public/ui/emoticon.svg`（矢量）做 **CSS mask 上色**，25×25（用户要求"别太小"）。
  SVG 自带 `fill="white"`，直接当图片用只能是白色；做成 mask 后颜色由 `background-color` 决定。

### 选择器：`UiPopover` + 两个页签

- 新增 `EmoticonPicker.vue`：挂在按钮上方（`UiPopover` 负责定位、Esc/点外部关闭、
  覆盖层登记、滚动跟随），面板内 `UiTabs` 分「黄豆 emoji」（85 格）与「深渊之歌第1弹」（8 格）。
- 网格**自己滚**（`max-height: min(46vh, 320px)`），不让整个面板滚——否则选到目录中段时
  两个页签会被滚出视野、没法换页签。
- **向右展开**：`UiPopover` 原先是"右边缘贴锚点"（靠右的锚点才合适），表情按钮在左下角，
  面板会伸到导航栏那边（用户反馈）。新增 `align` 属性（默认 `end`；`start` = 左边缘贴锚点、向右展开），
  表情选择器用 `align="start"`；吉祥物等既有用法行为不变。
- **选完直接关闭**并**把焦点与光标还给输入框**（用户要求；关掉就能接着打字）。
- 格子 tooltip / aria 是**中文名**（见「数据与解析」的中文名来源）。

### 富文本输入：表情在输入框里就是图片

- 输入框从 `<textarea>` 换成 `contenteditable`：`textarea` 只能显示文字，
  用户看到的是 `[e:tieba:tb_yiwen]` 这种内部代号（用户反馈）。
- **DOM 只是视图，`form.body` 才是真值**：`syncFromDom()` 把 DOM 序列化成 token 文本
  （文本节点原样、`<br>`/块级元素 → `\n`、表情取 `data-emoticon-token` 而不是 `src`），
  提交/计数/超长判断只看 `form.body`。
- 表情芯片是 `contenteditable="false"` 的 `<img>`（退格一次删掉整个表情），
  尺寸与正文**完全一致**（黄豆 1.45em、贴纸 64px）——用户要求"和发出去的大小一样"。
- 粘贴一律按**纯文本**插入（富文本会带进 `style`/站外图片）；复制时把选区还原成 token 文本。
- 踩到并修掉两个真问题：
  1. **芯片样式必须写在 `:deep()` 里**：芯片是 `document.createElement` 建的，
     拿不到 scoped 样式的 `data-v-*` 属性，`.comment-emoticon-chip` 匹配不上 →
     输入框里的表情**按原图大小**显示（240px 贴纸直接撑满输入区）；
  2. **光标位置只在输入框聚焦时记**（`keyup` / 框内 `mouseup`）：在 `focus`/`blur` 时记
     会拿到不可信的选区（重新聚焦时可能停在开头），实测表现为"第二次插入的表情跑到最前面"。
- ⚠️ 类名用 `.comment-editor` 而不是 `.comment-input`：后者是**历史遗留语义**
  （旧版评论框里的昵称/邮箱输入），`verify-comments-ui` 有一条"评论框内不再有昵称/邮箱输入"
  的断言正是靠它把关，不能占用。

### 详情页改用楼中楼 + 去掉「加载更多」

- **只改详情页**（图鉴、角色、魔物、副本…）：顶层评论 + 其下回复缩进块
  （B 站那种两层），收起时显示前 3 条 + 「全部 N 条回复 ▼」，展开变「收起 ▲」；
  回复楼内另一条时带「回复 @谁」，楼主有头像、**嵌套回复不带头像**（整块窄）。
- **站内讨论区保持不变**（聊天式平铺 + 引用行）：时间线是一维的，折叠会打破分页游标、
  滚动锚点与贴底跟随。前端用 `CommentsPanel` 的 `nested` 开关切换，`reverse` 下强制平铺。
- **服务端按顶层评论分页**（`?nested=1`）：只返楼主，每条附前 3 条回复与 `replyCount`；
  展开走 `?parent=<楼主 id>` 取整串。平铺分页做不到这点——一页里会有"父评论不在本页"的孤儿。
- **孤儿回复升级为顶层**：楼主被删/被隐藏后，回复它的人不该跟着消失
  （顶层查询里 `parent_id IS NULL OR 父评论不公开`），按 `replyTo: null` 显示「已不可见」。
- **去掉「加载更多」按钮**：改成滚到底自动加载（讨论区是往上翻到顶自动加载更早的）。
  分页方向跟着列表方向走：聊天式看顶部、列表式看底部。顺带把详情页"发表后整页重拉"
  改成"只把这一条并进去"——详情页现在也会加载多页，重拉会把翻出来的页丢掉。
- 两个实测被指出的问题：
  1. **「回复」跑到行中间**：`.comment-reply` 与 `.comment-delete` 各自 `margin-left: auto`，
     第一个 auto 外距把「回复」推到了中间。改成 `.comment-actions` 操作区**整块**贴行尾。
  2. **嵌套回复没有「删除」**：`syncOwned()` 只扫顶层评论，认领不到嵌套回复的删除令牌。
     改成连 `replies` / `allReplies` 一起扫。
- **试过又去掉**：详情页发表区 `position: sticky` 吸底（像 B 站 App）。
  实测浮层压住最后几条评论、观感很差（用户明确要求取消）。现在是普通文档流 +
  点「回复」时焦点回到输入框（浏览器会把聚焦元素滚进视野），既看得见输入区也不挡内容。
- 回归：新增 `verify-nested-replies.mjs`（28 项）。

### 回复：引用式（站内讨论区）

- **每条消息右侧加「回复」**（低对比、悬停提亮），点了以后发表区出现
  「回复 @昵称：摘录」条，`Esc` 或 ✕ 取消；发出的消息带一行引用（父昵称 + 摘录），
  点引用行滚到父评论并闪一下。
- **摘录是纯文字**：新加 `emoticonPlainText()`（`config/emoticons.js`，带单测），
  认识的表情写成 `[中文名]`——输入框放不下图，用文字最省地方也最不容易误读；
  列表里真正显示引用时仍然是图片。
- **数据用建表时就预留的 `comments.parent_id`，零迁移**（`schema.sql` 的注释同步更新）。
  不做嵌套树：聊天式时间线是**一维**的（分页、贴底跟随、滚动锚点都建立在这上面）。
- 读取用一次**自连接**（`LEFT JOIN ... AND p.status = 1`）：`AND p.status = 1` 不能少，
  否则已隐藏/待审的父评论内容会顺着引用行漏出来。代价是每页读行数翻倍（20 → 40 行），
  换来少一次往返。删除父评论**不级联**，回复留着、引用行退化成「回复的那条消息已不可见」。
- 写入端的 `parentId` 只做三条校验（正整数 / 同一页面 / 仍公开），**任一不满足就静默降级成
  普通评论**：用户点回复时对方可能刚好删了，把正文整条拒掉是最糟的体验。
- 「回复你」用**本机删除令牌**认领（`ownedIds`），不依赖账号系统。
- 发表区有两种挂载形态（详情页在 `CommentsPanel` 内部、讨论区在滚动容器之外），
  所以回复入口走两条链路：面板内有 `ref` 直接调、面板外经 `@reply` 事件转发给
  `DiscussionsView`——不这样做，讨论区就得把整份列表项复制一遍才能挂上回复按钮。
- 类名与断点：`replyable` 与 `readOnly` **解耦**（讨论区是只读列表但仍要能回复）。

### 发送方式：默认 Enter 发送（新增库组件 `UiSplitButton`）

- 「发布 ⌄」做成 `UiSplitButton`（左主操作 + 右细箭头，**外观是一个按钮**）：
  两个 `UiButton` 拼起来，调色板仍来自 `UiButton`，本组件改几何 + **整组状态**。
- 菜单两项：「按 Enter 键发送消息」（默认）/「按 Ctrl + Enter 键发送消息」，
  存 `localStorage` 的 `myrzg:comment-send-mode`（纯本机输入习惯，不进备份）。
- **输入法组词中的回车绝不发送**（`isComposing || keyCode === 229`）：拼音选词那一下回车误发最难受。
- 下拉开关**不受"内容为空"影响**（否则空输入时连发送方式都改不了）。
- 配色返工：第一版两半各自响应悬停/禁用（左半边悬停变亮、空输入时左半边 50% 透明），
  看起来像"两个贴在一起的按钮"（用户反馈"配色差异太大"）。改成**整组一起亮 / 一起暗**
  （禁用改为整组 0.55 透明度），下拉仍可点。
- **悬停只改底色、不动描边**：`UiButton` 自己的悬停会把描边换成青绿 `--accent-bright`，
  在这一对拼起来的按钮上很像"鼠标移上去就冒出一条线"（用户反馈"很怪"）。
  本组件在自己的悬停规则里把描边钉回静止态那条。
- **箭头会翻向**：新增 `is-expanded`，展开时细箭头旋转到朝上、收起朝下（0.16s 过渡，
  `prefers-reduced-motion` 下不参与动画）——"展开/收起"要有方向上的反馈。
- **手机端只留「发布」**（≤767px 隐藏箭头与发送方式开关，并补回主按钮的右侧圆角）：
  手机没有物理回车键，这个开关没有意义；断点与 `ChaptersView` 的 `MOBILE_QUERY` 一致。

### 选择器面板：固定高度（像 QQ 一样）

- 网格高度从 `max-height: min(46vh, 320px)` 改成**固定 `height`**：两个页签格数差很多
  （85 vs 8），高度跟着内容走的话切页签整个面板会忽高忽低地跳（用户要求"保持相同高度"）。
- 固定高度后格数少的页签下方留白，与 QQ 表情面板一致；另加 `scrollbar-gutter: stable`，
  避免滚动条出现/消失让格子轻微错位。

### 库组件收口：`UiPopover` 的关闭按钮统一规格

- 原先是 `<UiButton variant="ghost" size="sm">×</UiButton>`，渲染出来是 **34×28 的长方形**
  配 **12px** 的 `×`；`UiModal` 的关闭钮是 **28×28 方形**配 **14px** 的 `✕`。
  小面板（发送方式 240px）里这个差异很明显（用户反馈"这个叉大小不对"）。
- 统一成弹窗那一套：28×28 + `14px` + `✕`，悬停字色加深，`aria-label` 也从
  「关闭选择窗口」统一成「关闭」。

### 渲染落点：四处统一

| 位置 | 处理 |
| --- | --- |
| 讨论区 / 图鉴详情的评论列表 | `CommentsPanel` 改用 `EmoticonText` |
| 右栏「最新讨论」 | `App.vue` 的 `.recent-body` 改用 `EmoticonText`，**多套一层 inline 容器** |
| 管理端 | `AdminCommentsView` 的 `.admin-body` |
| 账号弹窗 | `AccountModal` 的「我的评论」与删除确认引用 |

- 新增 `EmoticonText.vue`：文字段用**裸文本节点**输出（父级 `white-space: pre-wrap` 才能继续
  保留换行与连续空格），token 换成 `<img>`；**目录外的 token 当普通文字**原样显示；
  图挂了回退成**中文名**（不是 token 原文），便于判断是素材没到位还是内容丢了。
- 尺寸按包分两类：黄豆跟随正文字号（1.45em，混排不撑行）、游戏贴纸固定 64px。
- 右栏是 `display:-webkit-box` 的两行截断，直接塞 `<img>` 会被当成 box item 竖着堆，
  所以包一层 inline span（`.recent-body-text`）让图片回到正常行内排版，
  并把表情压到 1.1em / 34px，避免把两行截断撑开（实测带表情的长正文仍 53px ≈ 两行）。

## 数据与解析

### token 格式：正文里存 `[e:包:名]`

- **正文仍是纯文本，没有新增数据库列、没有改任何接口契约**。表情写成一段普通字符：
  `[e:tieba:tb_yiwen]`、`[e:abyss1:syzg_angry]`。
- 为什么不是 unicode / 路径 / 新列：黄豆与游戏表情都是**图片**（Unicode 里没有码位）；
  存路径会随素材目录整理成批变死链（与"头像存 ID 不存路径"同理）；
  新列还要改 schema 与四个接口的序列化，且丢失"表情在文字中的位置"。
- 新增 `src/config/emoticons.js` 作为**唯一来源**：表情包目录、token 语法、
  显示字数统计、分段函数。**零依赖纯函数，服务端直接 import 同一份**
  （Worker 与前端计长口径不允许出现第二套实现）。
- 服务端只校验 token **格式**、不校验是否在目录里（Worker 读不到 `public/`，同头像 ID 的口径）；
  目录外的 token 渲染时当普通文字，无害。token 只含 `[a-z0-9_:]`、不含 `<`，
  不影响审核词表的「外链」「HTML 标签」两条规则。

### 素材换成用户整理过的新包（含中文名）

- 黄豆：改用 `贴吧经典黄豆表情包` 的两个子目录——**`tb_黄豆表情`（60）在前、
  `tb_物品与符号`（25）在后**（用户指定顺序），表情名改用拼音文件名（如 `tb_yiwen`）。
- 《深渊之歌》第 1 弹：重新导入**去背景版**（同名 `syzg_*.png`，像素更新）。
- **中文名有据可查**，不是回忆出来的：
  1. 与包内 `经典命名版`（50 张人工命名的 `NN_名称.png`）**逐张像素比对**得到 50 条
     （`tb_yiwen` ← `15_疑问.png`，与用户举的例子一致）；
  2. 其余 35 条按包内拼音命名 + **逐张看图确认**
     （`tb_wuzuixiao` 拼音有歧义，看图确认是「捂嘴笑」）。
  名字与顺序手写在目录表里，导入脚本双向核对（缺图 / 漏登记 / 缺名字都报错），
  单测新增"同一包内不允许重名"（悬停提示要用它）。
- 合计 **93 张**（85 黄豆 90×90 + 8 贴纸 240×240），统一导入为**无损 WebP**
  （像素与原图一致，不属于"压缩"，因此不需要压缩授权），约 590 KB。
  源 PNG 原样留在维护目录。
- 导入脚本 `scripts/dev/import-emoticons.mjs`（默认预览、`--apply` 才写）：
  **同时接受 `.png` 与 `.webp`**（维护目录可能已被就地转过格式），
  且 `--apply` 会**清理本包目录里不在目录表内的旧文件**
  （换命名方案时留下的 85 个 `image_emoticon*.webp` 就是这一步清掉的）。
- 双向核对在首次运行时抓到一次真实偏差：第 1 弹的源文件名是 `syzg_angry.png`
  而不是 `angry.png`（前一次目录列举被控制台宽度截断，看成了 `angry.png`）。

### 字数上限改为「显示字数」，一个表情算 1 字

- 一个 token 有 7~25 个字符，按原始字符计数的话插三个表情就吃掉几十字、与观感完全对不上。
  现在 `MAX_BODY = 200` 是**显示字数**：认识的表情算 1 字，其余按 `String.length`。
- 服务端两道显式闸门（`functions/api/[[path]].js` 的 `createComment`）：

  | 闸门 | 阈值 | 依据 |
  | --- | --- | --- |
  | 原始长度（`sanitize` **之前**判断） | `MAX_BODY_RAW = 8200` | 200 × 语法允许的最长 token 41 字 |
  | 显示字数（sanitize 之后复核） | `MAX_BODY = 200` | 用户可见的限制 |

  原始闸门放在截断之前：`sanitize()` 结尾是 `.slice()`，先截断再校验就可能把一个 token
  砍成 `[e:tieba:tb_yi`（少了右括号），那条评论会**永久损坏**——比"少几个字"严重得多。
- 富文本输入没有 `maxlength`（它只能卡原始字符数），200 字限制由计数器 + `canSubmit` 表达：
  超限时计数器变红并给出与服务端同一句提示、禁用「发布」。
- 实测 200 个表情（原始 2200 字）可正常发表且正文未被截断。

## Bug 修复

### 表单里的 `UiButton` 其实是隐式 `submit`（点表情按钮把表单提交了）

- **现象**：点「插入表情」不只是打开面板——输入框被清空、还多发了一条评论；
  按钮自己的 `@click` 完全正常（面板确实打开了），所以第一反应是查插入逻辑。
- **根因**：`UiButton.vue` 声明了 `type` prop，**模板里从来没绑定**，渲染出的 `<button>`
  没有 `type` 属性；在 `<form>` 内它默认就是 `type="submit"`。于是这个"图标按钮"其实是提交按钮：
  点它 → 浏览器提交表单 → 表单的 `@submit.prevent="submit"` → 完整走了一遍发表流程。
- **解法**：模板绑定 `:type="type"`（默认 `button`）。全仓只有 `CommentComposer.vue`
  一个 `<form>`，所以只影响这一处；「发布」按钮本来就靠 `@click="submit"`，不依赖隐式提交。
- 排查与检查清单记入 [KNOWN_BUGS_AND_FIXES 第 12 条](../../../context/RISKS.md#23-组件与交互)。

### 全局图片 error 兜底会吃掉组件自己的 `@error`

- **现象**：表情素材加载失败时，本该回退成文字（好判断是素材没到位），实际却显示成
  通用的 `/ui/visibility-off.svg` 占位图标（"眼睛被划掉"）。
- **根因**：`App.vue` 的 `handleGlobalImageError` 注册在 **document 捕获阶段**，
  它把失败的 `<img>` 换成兜底图后还 `stopImmediatePropagation()`——组件自己的 `@error`
  **根本不会执行**。框架预留的出口是 `data-image-fallback="custom"`（FurnitureCard 等在用）。
- **解法**：`EmoticonText` / `EmoticonPicker` / 输入框芯片都带上该属性，自己处理失败。
- 这条 bug 是被回归脚本"逼"出来的：原先断言"当前 `complete` 的图有几张"，
  兜底图也算"加载成功"，所以 113/113 是假绿；改成**按目录表逐个 `fetch` + `createImageBitmap`
  解码**之后，缺图立刻暴露（当时才发现 28 张素材真的不在盘上）。

### 发完表情消息不自动滚到底部（用户反馈）

- **复现**：列表贴底（gap 0）→ 输入区插入一个贴纸（发表区被撑到 180px，聊天区可视高变小，
  gap 变 108）→ 发表（发表区收回、列表 +1 条约 124px 高）→ **gap 124，停在半空**。
- **根因**：自动跟随的判据 `isNearBottom()`（阈值 120px）是在 `flush:'post'` 的 watcher 里
  **插入之后**现算的。文字消息约 78px 还不至于跨过 120px，但**表情/贴纸消息有 124px 高**，
  于是一个明明贴在底部的用户被算成"已经翻上去了" → 不跟随。
- **修法**：维护 `nearBottomBeforeInsert`（滚动事件里刷新；插入前的那一刻就是它），
  watcher 只看这个值；另外在滚动动画结束后加一个 **0.9 秒落定窗口**
  （表情图片解码、字体回退可能在这之后才改高度）。
- 落定窗口第一版是"每帧强制贴底"，结果与外部滚动打架——`verify-post-scroll` 的场景 B
  （往上翻历史时发表，要求列表原地不动）被它反复拽回底部。改成
  **"只在内容高度又变了时补一次 + 位置已被挪走就立刻退出"** 后 B2 恢复 12/12。
- 顺带：滚轮/触摸/按键这类**只可能来自用户**的事件会立刻中断跟随
  （只靠 `scroll` 事件分不清程序滚动与用户滚动）。

### 详情页发的评论混进了右栏「最新讨论」（用户反馈）

- **现象**：在物品详情弹窗的讨论区发一条，右侧「最新讨论」立刻出现同一条；
  刷新或等 15~30 秒后它又自己消失（用户："我在详细页发的，右边怎么也能收到？"）。
- **根因**（两个条件叠加）：
  1. **服务端是对的**：`/api/recent` 只查 `page_key = 'site:general'`，所以刷新后就没了；
  2. 前端"发表后直插一条"的 `addRecentComment` **无条件插**。它的注释写着
     "站内讨论区在本站是唯一评论入口，所以新评论一定属于 `site:general`"——
     图鉴详情弹窗也有讨论区（`item:xxx` / `hero:xxx`…）之后，这条假设就不成立了；
  3. 而且它**想过滤也过滤不了**：`POST /api/comments` 返回的 `comment` 没有 `pageKey`
     （两个 GET 接口都有），消费方无从判断这条属于哪个页面。
- **解法**：`POST` 的 `comment` 补 `pageKey` / `pageLabel`（与列表接口同形状）+
  `addRecentComment` 里判 `pageKey !== SITE_PAGE_KEY` 直接不插。
- 断言加在 `verify-comments-ui.mjs`（物品详情那条链路）：
  "物品页发表的评论**不**混进右栏「最新讨论」"。
  顺带发现这个 bug 还会把详情弹窗的发表区**顶出视口**（同一处断言暴露），修完一起好了。
- 教训记入 [KNOWN_BUGS 第 14 条](../../../context/RISKS.md#22-聊天式列表)：
  "本地直插"必须带上与列表接口一致的过滤条件；写入响应与列表响应字段不一致时先怀疑它。

  讨论区基本只有自测），所以没有做兼容别名；若将来再换命名方案，需要先加一层旧名映射。
- ⚠️ **Android 老包**：`public/images/**` 走 CDN 优先，在线时会自动拿到新素材；
  但**离线**且热更包未更新时，新表情会回退成中文名文字（不显示破图）。
  要让老包离线也有表情，需要发一次热更包（与既有的 P0 待办同一件事）。
- 回退：`git revert` 本日提交即可回到"没有表情入口"的状态；已发表的表情评论会退回
  显示 `[e:包:名]` 原文（不会崩，但观感退化）——**如果已经有用户发表过表情，回退前先考虑保留渲染**。
