## 🔴 线上事故：验证码邮件一封都发不出去（已修复并部署）

**现象**：用户在生产注册页点「注册并登录」，界面提示「验证码已发出」，
但**邮件始终收不到**（用户提供的截图里最新两封验证码是昨天的，今天没有新的）。

**根因**（直接打腾讯云 SES 复现，用无效收件人 `@example.invalid` 避免真发信）：

```
Unsubscribe: 0     -> Code=InvalidParameter
                      Message=The value type of parameter `Unsubscribe`
                              is not valid, input type should be `string`
Unsubscribe: '0'   -> OK（正常返回 MessageId）
```

腾讯云 SES 对 `Unsubscribe` 做**严格类型校验**，传数字会**整封拒收**。
⚠️ 但 `TriggerType: 1` **接受数字**（实测正常）—— 只有 `Unsubscribe` 要求字符串，
所以不能"统一成一种类型"。已改为 `'0'`。

**为什么这个 bug 极难发现（三个条件叠加）**：

1. 发信在 `context.waitUntil` 里**异步**执行，失败只写服务端日志；
2. 接口照样返回 `sent: true`，`auth_codes` 表里**也有那条记录** —— **查库完全看不出问题**；
3. 本地/端到端测试全是绿的，因为 `MAIL_STUB=1` 时**根本不发信**。

**排查路径**（都基于可复现证据，不靠猜）：

| 步骤 | 结论 |
| --- | --- |
| 生产 `/api/health`、`/api/auth/salt`、`/api/auth/captcha` | 全部 200，接口正常 |
| `auth_codes` 表 | 有记录，`created_at` = **今天 19:02:15**（说明代码确实跑到了发信那步） |
| `sqlite_sequence`（**关键**） | `auth_codes seq:3`、`comments seq:25`、**`users` 无记录** |
| `wrangler pages secret list` | `TENCENT_SECRET_ID/KEY` 已配、`MAIL_STUB` 未设（配置正确） |
| 直连 SES 复现 | 拿到 `InvalidParameter`，定位到 `Unsubscribe` 类型 |

**回归**：新增 `tests/unit/mail-payload.test.mjs`（4 条）锁住送出去的 payload 形状
（`Unsubscribe` 必须字符串、`TriggerType` 保持数字、`TemplateData` 必须 JSON 字符串、
失败必须有日志）。**已反向验证**：把 `Unsubscribe` 改回数字即变红。

**部署**：`e681fe69`，推送后 Cloudflare Pages 自动构建完成（已用 `pages deployment list` 确认）。

### 关于「用户是不是被我删了」—— 没有，而且从来就没有过用户

用户看到后台「用户」页是空的，怀疑数据被删。查证结论：**生产库从未成功注册过任何用户**。

判据是 `sqlite_sequence`（SQLite 记录**历史最大自增 ID**，**删除数据后仍然保留**）：

```
auth_codes  seq: 3     ← 历史上只生成过 3 个验证码
comments    seq: 25    ← 建过 25 条评论
users       （无记录） ← 从未成功 INSERT 过任何用户
```

若曾经有用户、之后被删，`users` 会留下 `seq` 行。它**完全不存在**，
所以不存在"被谁删了"这回事 —— 上面那个发信 bug 才是"注册一直不成功"的真正原因。

### ⚠️ 一条方法论教训：别信单次运行

排查 `app-shell.spec.js` 的 `page.goto('/#/heroes')` 超时时，我先跑一次 baseline 得到
「31/31 通过」，据此判断「是我的改动弄坏的」，然后花了几轮逐文件回退去定位。

**实际两边都会红**：baseline run1 失败、run2 通过；我的版本 4 次里 3 红 1 绿。
根因是 `waitUntil:'load'` 等不到 `readyState=complete`——这台机器上大量图片请求长期挂起
（实测 38 个 pending，含 `ui/*.webp` 与按需 chunk），属**环境性能导致的既有抖动**，
与本次改动无关。

教训与交接文档那句「别信任何二手清单，自己跑一遍」是同一回事的另一面：
**单次运行也不是证据**，判断「谁弄坏的」至少要在两边各跑两遍。
本轮真正可靠的结论都来自**可重复的产物断言**（单测 268/0、`verify` 全绿、逐文件等价比对）。
