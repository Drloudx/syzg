# 2026-10-09 追加：模拟招募「分享」改为截图分享

## UI 与交互

- **招募结果页「分享」按钮**（`GachaResultPanel.vue`）：原先只把结果摘要**复制到剪贴板**，
  现改为**把本次结果合成为一张 PNG 再调起分享**，与游戏内行为一致。
  - 合成入口 `src/utils/gachaShareImage.js`（新增）。
  - 原生端：写 Cache 目录后 `Share.share({ url })`（与「导出数据备份」同一套做法）。
  - 网页端：优先 `navigator.share({ files })` 弹系统分享面板；不支持或失败则退回下载。
  - 文件名 `模拟招募-<时间戳>.png`；提示文案随分支显示「已调起分享」/「已保存图片」。

## 实现要点

- **逐图层按 DOM 实测矩形取位**，不重抄一遍 CSS 常量：卡片有 10 个图层、百分比定位写在
  `.rd__*` 里，抄一份以后改样式会**静默画歪**（截图与页面不一致且不报错）。
  改为读 `getBoundingClientRect()` + `object-fit` / `filter` 的 computed 值，样式改动截图自动跟随。
- 背板的 `filter: brightness(2.1)` 与 `object-fit: cover` 从 computed 读取后施加到 canvas。
- 输出倍率 2×（设计画布 1534×750 → 3068×1500）。
- 图片按 `src` 缓存解码结果（10 张卡共用同品质底板/边框）；`crossOrigin='anonymous'` 是必须的
  ——原生端图片走 CDN 绝对地址，不带会把 canvas 污染、`toBlob` 抛 `SecurityError`。

## Bug 修复

- **误传舞台会静默合成空气图**：页面上同时存在多个 `.gacha-stage`（卡池面板那个仍挂载着），
  `querySelector` 全局搜索会命中错的那个，跑完不报错但产出全透明图（实测 `opaqueRatio: 0`）。
  已在 `renderGachaResultImage` 加断言：舞台必须含 `.result-diamond`。
- **`navigator.share` 挂起导致点了毫无反应**：实测无 UI 环境（自动化浏览器）里 share
  **既不 resolve 也不 reject**，于是失败兜底永不执行。已加 20 秒超时，把"挂起"转成"失败"再退回下载。
- 用户主动取消（`AbortError`）**不**退回下载 —— 尊重用户选择，不偷偷下载文件。

  - 实测：电脑点分享 **524ms** 出图（原需等超时）。

## 重构与维护

- **合成器泛化为两池共用**（原先写死角色池的选择器）：
  - 改为「遍历整棵子树 + 按 `z-index` 路径排序 + 按元素类型分派」，两池各传一个 `requireSelector` 做校验。
  - 为什么要按 `z-index` 而不是 DOM 顺序：舞台是绝对定位分层（背景 1 / 桌面 3 / Spine 5 / UI 10+），
    DOM 顺序与视觉层级不一致，照 DOM 画会出现错层。
- **`gachaSpinePlayer` 新增 `renderNow()` / `renderSharedSceneNow()`**：
  - WebGL 上下文未开 `preserveDrawingBuffer`（开着有持续 GPU 开销），浏览器合成后清空绘制缓冲，
    隔帧 `drawImage(canvas)` **永远得到空白**（实测采样点全 0）。必须在同一任务里先同步重画再抓。
  - 抽出 `drawScene(delta)` 供渲染循环与 `renderNow()` 共用；`renderNow` 传 `delta=0`，不推进动画。

# 2026-10-09 追加：批量多选 / 审核词表超管可维护 / 按命中原因筛

## 一、评论批量多选

- 评论列表加复选框（行首 + 表头全选）与批量操作栏：批量放行 / 隐藏 / 转待审 / 取消选择。
- 后端 `PATCH /api/admin/comments` **同一接口**支持 `ids` 数组与单条 `id`，语义一致；
  单条形态**向后兼容**（老调用不受影响）。
- 上限 100 条（`BATCH_MAX`），理由是**防手滑**而非性能：全选几百条难以复盘。

| 设计点 | 取舍 |
| --- | --- |
| 选择**不随筛选/翻页清空** | 允许"第 1 页选几条、翻页继续选"；代价是"选了看不见"，用常驻条数 + 取消选择补偿 |
| 不存在的 id **跳过并回报** | 选了 10 条其中 2 条被同事删掉，剩 8 条照处理；`missing` 字段告诉调用方 |
| **逐条写审计**而非一条摘要 | 评论行没有记录操作者的列，只有逐条审计才能在账本里按单条追 |
| 批量与单条同一接口 | 分开会让人以为两者规则不同（锚点、备注、审计口径其实一致） |

## 二、审核词表超管可维护

- 采用「**代码基线 + 数据库叠加**」，而不是把词表整表搬进库。
- 新表 `review_keywords(category, text)` + `review_category_flags(category)`；
  `GET /api/admin/review-keywords`（所有管理员可读）/ `PUT`（**仅超管**，整表替换）。
- 后台设置页新增词表编辑器：类别启用开关、加词、删词、新建类别。

### 为什么不整表搬进库（两条硬理由）

1. **安全**：不允许在网页里编辑**正则**。写错一个字符 → `new RegExp` 抛错 →
   `POST /api/comments` **全站 500**；写得回溯爆炸 → Workers CPU 超限。
   库里存**普通关键词**，运行时 `escapeKeyword()` 转义后拼进正则，两类事故都不可能发生。
2. **可用性**：基线在代码里 → 库读不到 / 迁移没跑时**基础防护照旧**；
   全搬进库则等于"库一有问题就不审核"。

### 性能

`matchReview` 跑在**每一条评论提交的关键路径**上。若每次都读库，发评论就多一次
数据库往返（还烧 D1 配额）。故加**模块级内存缓存 + 30 秒 TTL**，同一 Worker 实例内
绝大多数请求零额外查询；`PUT` 后清本实例缓存，**改的人自己立刻看到效果**。
自定义词按类别拼成**一个**正则（不是逐词 `test`），匹配成本与基线同级。

## 三、按命中原因 / 人工备注筛

- `GET /api/admin/comments?reason=<类别>&hasNote=0|1`；
  `reason=any` = 命中过任何词。
- `review_reason` 存的是**逗号分隔的多个类别**，所以用 LIKE 子串匹配而非等值。
- 前端加两排筛选：命中原因（全部 / 自动命中 / 赌博 / 引流 / 外链）、人工备注有无。

# 2026-10-09 追加：缓存层补测 + 匹配开销实测

## 背景

性能设计（内存缓存 + TTL）此前**只有实现、没有测试**：
`tests/unit/review-keywords.test.mjs` 覆盖的全是 `buildMatcher` / `matchReview` 这类纯函数，

同时，"开销≈0"当时是**推理**而非实测 —— 补了两件事。

## 一、缓存层补测（新增 6 条）

| 断言 | 守的是什么 |
| --- | --- |
| 连续取 3 次**只读库 1 次** | 缓存真的命中；退化成每次读库不会报错，只会悄悄变慢并烧配额 |
| **并发 5 次只读库 1 次** | `inflight` 合流；否则一波流量会各自打一次 D1 |
| 读库失败**回落基线且不抛错** | 不能把"配置故障"放大成"全站发不出评论" |
| 失败后**不长期缓存坏结果** | 一次网络抖动不该让词表很久不更新 |
| `invalidate` 后**立刻生效** | 超管保存后自己马上看到效果 |
| **TTL 到期才重读** | 其它实例最长 30 秒跟上的既定代价 |

- 为让 TTL 那条能秒级验证，加了 `setCachedAtForTest(ts)`（**仅测试用**，把时间戳往前拨，
  等价于"等了 30 秒"；真 sleep 30 秒会让测试无法接受）。
- **反向验证**：移除缓存命中判断 → 「只读一次库」与「TTL 到期才重读」**两条翻红**，
  证明测试不是空转。

## 二、匹配开销实测（替换掉原来的推算）

用 `process.hrtime.bigint()` 测 20 万次取均值（含预热排除 JIT）：

| 场景 | 每条评论耗时 | 占免费版 10ms 预算 |

| 加满 300 条自定义词（上限） | **0.000398 ms** | 0.0040% |
| 上限场景且命中 | 0.000437 ms | — |

- 300 条自定义词的增量：**+0.000048 ms/条**（相对基线 +13.7%，绝对值可忽略）。
- 🔴 关键结论：**缓存消掉的那次 D1 往返（约 5~30ms）比匹配本身大四个数量级** ——
  这正是不把词表读放进热路径的原因。匹配成本不是问题，**数据库往返才是**。

## 用户反馈暴露的一个显示缺陷（我方 bug）

用户打开设置页后问：**"当前没有默认的词条吗，必须都得自己加吗？"**

- **事实**：每个内置类别都有一批内置词（合计 90 个），一直在生效。
- **缺陷**：界面只显示"自定义 N 条"，**完全没展示内置词** ——
  于是"自定义 0 条"让人读成"这个类别是空的"，进而以为必须自己加词，甚至据此判断某个类别没用。

### 修复

- 后端 `GET /api/admin/review-keywords` 的每个类别新增 `baselineWords`（内置词列表）。
- 新增 `listBaselineWords(category)`：把类别正则**拆成可读词**。
  界面刻意**不显示正则源码** —— 那会让人以为自己在编辑正则，而实际库里存的是普通词、
  运行时才转义拼接（见 ADR 122）。展示与匹配是两条独立的路。
- 界面：内置词用**灰底虚线**渲染、无删除按钮；`自建类别` 与 `内置 N 词` 分别标注。
- 补说明：内置词不能单独删（在代码里），**取消勾选整个类别**才是等价操作，且可随时勾回。

## 「违禁药」并入「违禁品」（不是删除）

用户最初的要求是"违禁药这一块删了吧"。先做了删除，但**脚本立刻报出后果**：

```
垃圾样本漏检：1/5
  ⚠️ 漏检 ← 出售壮阳药，货到付款
```

删除等于那 22 个词（毒品/大麻/伟哥/催情…）不再拦，含这些词的广告会**直接公开可见**。
改为**合并**：词一字不减地并入「违禁品」，只是命中原因显示成「违禁品」。

- 核对依据：生产库 `review_reason LIKE '%违禁药%'` 命中 **0 条**，改名不会让历史数据的命中原因对不上。
- 结果：`违禁品` 从 **4 词 → 36 词**；垃圾样本恢复到 **0/5 漏检**。
- `scripts/dev/sync-comment-blocklist.mjs` 的「出售壮阳药」样本**保留并加注释** ——
  它现在守的是"合并后的词仍然有效"，谁误删了这批词它就会翻红。

| 选项 | 拦截能力 | 命中原因显示 | 结论 |
| --- | --- | --- | --- |
| 直接删除 | ❌ 丢 22 个词 | — | 广告会漏 |
| **并入违禁品** | ✅ 不减 | 「违禁品」 | **采用** |
| 只停用（后台开关） | ✅ 不减 | 仍显示「违禁药」 | 可行，但词仍在代码里、界面上仍占一个类别 |

# 2026-10-09 追加：封禁理由

## 背景

后台能力盘点里发现的一处**不一致**：评论「转待审」已支持填写原因，
但**用户封禁没有** —— 同样是"处理某人/某内容"，一处能说明为什么、一处不能。

## 实现

- 迁移第 8 步：`users.ban_note TEXT DEFAULT NULL`。

- `/api/admin/users` 列表返回 `banNote`；封禁按钮改为弹 `UiModal` 填写理由，解封仍用轻量确认。
- 列表把理由显示为「封禁理由：…」（与评论的「待审原因：…」同色系）。

## 与评论「转待审原因」**共用同一套语义**

| 规则 | 说明 |
| --- | --- |
| 可空 | 有时就是"例行停用"，不强制填 |
| 状态反转时**服务端清空** | 解封 = 状态已定论，留着旧理由会误导后来人 |
| 历史由 `admin_audit` 留存 | 每次封禁写一条，detail 里带理由 |
| 规范化共用 | 直接复用 `normalizeReviewNote()`：trim、换行折空格、超长回 400 而非截断 |

- 复用同一个函数是刻意的：两处规则若各写一份，迟早漂移。

## 🔴 为什么理由**只给管理员看**

用户登录被拒时仍只看到 `AERR.banned`「该账号已被停用」，**不返回理由**。

- 把理由透给刷广告的人，等于**把审核标准公开**（"原来写到第几次才封""原来这个词会被拦"）。
- 已用测试守住：`/api/auth/me` 的响应里**不含 `banNote` 字段**。
- 代价：用户不知道自己具体为什么被封。若将来想做成"告知用户"，需要另加一个刻意开放的字段，
  **不能**直接把这一列暴露出去。

# 2026-10-09 追加：评论被处理通知（作者侧红点）

## 要解决的问题

作者的评论被隐藏 / 打回待审后，**他并不知道** ——
「我的评论」里其实一直有「待审核 / 已隐藏」标签，但他没有理由主动去看。
结果就是"我的评论怎么没了"。

**所以缺的不是数据，是"他不知道自己该去看"** —— 加一个未读红点即可，
不必新建通知视图。

## 性能（用户明确问过）

**几乎不影响**，因为复用了项目里已有的机制、且触发时机相同：

| 项 | 已有的「谁回复了我」 | 新增的「评论被处理」 |
| --- | --- | --- |
| 存储 | 1 个时间戳字段 | 1 个时间戳字段（对称） |
| 查询 | JOIN 两张表的 COUNT | **单表** COUNT（更便宜） |
| 写入时机 | 每次有人回复 | 只在管理员处理评论时 |
| 查询时机 | 打开账号弹窗时 | 打开账号弹窗时（相同） |

- **不建通知表**：未读数 = `COUNT(我的评论 WHERE moderated_at > 我上次读的时间)`，
  与 `users.replies_read_id` 同一套思路（少一张表、少一次写入）。
- 未读数只在**第一页**算（`!cursor`），翻页不重算。

## 实现

- 迁移第 9 步：`comments.moderated_at` + `users.moderation_read_at`
  + 索引 `idx_comments_user_moderated(user_id, moderated_at)`。
- `GET /api/auth/comments` 返回 `moderatedUnread`；
  新增 `POST /api/auth/comments/read` 标已读。
- 账号弹窗「我的评论」那行显示红点；**点进去即视为已读**
  （与「谁回复了我」同一时机：由用户主动点进来那一刻算起）。

## 🔴 修掉一个**真实的丢通知缺陷**（且踩了两次坏方案）

未读判定是 `moderated_at > moderation_read_at`。三个方案对比：

| 方案 | 后果 |
| --- | --- |
| 两边都用**秒** | 同一秒内"标已读 + 又被处理"落到 `S > S`（假）→ **通知被静默吞掉** |
| 秒 + 基准**退 1 秒** | `S > S-1` **恒真** → **红点清不掉**，要再点一次才清 |
| **两边都用毫秒**（采用） | 冲突窗口从 1 秒压到 1 毫秒，两个方向的错都不再出现 |

- 实测证据（第一版秒级）：
  `moderated_at = 1791706961`、`moderation_read_at = 1791706961`、差值 `0` → 未读数 `0`。
- 我**先写了"退 1 秒"的修法**，跑到测试才发现它把"红点清不掉"换了出来 ——
  两个方向各错一半，**根因是秒级精度不足以区分先后**，所以最终改成毫秒。

## 同类问题：`POST /api/auth/replies/read`（同一日**已修**）

「谁回复了我」当时有**同样的秒级边界**：判定用
`comments.created_at > users.replies_read_at`，两边都是秒。

- 当时不顺手修的理由：基准退 1 秒会让红点清不掉；改毫秒则要动 `comments.created_at`
  （全站都用秒），牵动面远超那次范围。
- **解法不是毫秒，是换基准到评论 id**（`users.replies_read_id`）。
  `comments.created_at` 是既有的秒级列、全站共用，只把基准换成毫秒会让
  `S > S_000` 恒真 → 红点永远清不掉（等于把 bug 换个方向）。`comments.id` 是
  AUTOINCREMENT、严格单调（实测 0 处与 `created_at` 逆序），两个方向的错同时消失。
- 迁移第 10 步 `scripts/sql/2026-10-09-replies-read-id.sql`：加列 + 按旧语义回填
  （`replies_read_at IS NOT NULL` 的 118 个用户换算成 id；未标过已读的保持 NULL）。
- 回归测试 `tests/api/comments-auth.mjs` 【7b】：循环若干轮**只在确证撞进同一秒时断言**，
  且同时校验"标已读整段请求落在同一秒"（只验回复落秒会假通过）。反向验证过：
  临时改回秒级基准 → 该条变红（`unread = 0`，通知确实被吞），改回即绿。

# 2026-10-09 追加：「谁回复了我」未读基准改 id + 404 测试归位

## 一、未读基准从时间改成评论 id（`users.replies_read_id`）

## 背景

同日下午修「评论被处理」通知时，发现「谁回复了我」有**同一个秒级边界**：
`comments.created_at > users.replies_read_at`，两边都是秒 → 同秒内"标已读 + 收到回复"
落到 `S > S`（假）→ **通知被静默吞掉**。当时标为"既有行为，未修"。

本次修掉，但**解法与「评论被处理」不同**：

| | 「评论被处理」 | 「谁回复了我」 |
| --- | --- | --- |
| 基准列 | `comments.moderated_at` / `users.moderation_read_at` | `users.replies_read_id` |
| 基准类型 | **毫秒**时间戳 | **评论 id** |
| 为什么 | 两个列都是本功能独占、上线即带毫秒 | 见下 |

**为什么这边不能用毫秒**：`comments.created_at` 是**既有的秒级列**，全站（列表排序、
时间显示、限流）都在用。只把基准换成毫秒 → `S > S_000` 恒真 → **红点永远清不掉**，
等于把 bug 换个方向。`comments.id` 是 AUTOINCREMENT、严格单调，两个方向的错同时消失。

## 实现

- `authMyReplies`：未读判定改 `AND c.id > ?2`（基准 `replies_read_id`）。
- `authMarkRepliesRead`：不再写 `ts`，改写
  `MAX(c.id)` over 自己的可见回复 —— **不是** `last_insert_rowid()`（那是全局的，
  会越过自己的回复范围，把别人的评论也算成已读）。
- `schema.sql`：新增 `replies_read_id`；`replies_read_at` 标注废弃（保留作回填来源）。
- 迁移第 10 步 `scripts/sql/2026-10-09-replies-read-id.sql`：加列 + 按旧语义回填。
  本地实测：回填 **118** 个用户，`replies_read_id IS NULL AND replies_read_at IS NOT NULL`
  剩 **0** 个；未标过已读的保持 NULL（= 全未读，与旧代码把 NULL 当 0 一致）。

## 验证

- `tests/api/comments-auth.mjs` 【7b】新增：循环若干轮，**只在确证撞进同一秒时断言**。
  🔴 守卫有两道，缺一会**假通过**：只验"回复落在第二 S 秒"不够 ——
  若"标已读"落在 S-1 秒，旧实现 `S > S-1` 为真、未读数照样是 1，旧代码也能过。
  所以还要验"标已读**整段请求**都在 S 秒内"（前后采样取整相同），两条合起来才确证
  `read_at === created_at === S`。
- **反向验证**：临时把两处改回秒级基准 → 【7b】变红（`unread = 0`，通知确实被吞），
  其余全绿；改回即绿。证明这条测试是真守卫，不是同义反复。
- `tests/migration/rehearse.mjs` 加第 10 步 + 4 条结构断言 + 3 条回填语义断言
  （换算正确、不凭空造未读、未标过已读的不被回填），夹具自带清理。
  演练 **66 / 0**。
- 同步修正 `replies_read_at` 的过期表述：`authSession.js`、`AccountModal.vue`、
  `ACCOUNT_SYSTEM.md`（schema 片段 + 路由表）、`DECISIONS.md` ADR 132、
  本日志上文。ADR 132 里"⚠️ 未修"那条改指向新增的 **ADR 134**。

## 二、404 测试归位（见上文「一个非本次引入的既有失败」）

**改的是测试，不是产品**。`tests/ui/account-modal.spec.js` **44 / 0**。

# 2026-10-09 追加：用户列表「评论数」可点进去

  取消时**同时清掉 URL 上的 query**（否则刷新又会被筛回来，用户以为"取消没生效"）。

## ⚠️ 一处**我自己先前的错误说法**（已核实并修正）

盘点时我把这个入口的理由写成"**防重名** —— 昵称可以重复、会混进别人的评论"。
**实测证明这个理由站不住**：

| 核实项 | 结果 |
| --- | --- |
| `users.nick` 约束 | **UNIQUE**（全站唯一），建两个同名账号会 409 |
| `comments.nick` 里同昵称属于不同账号的情况 | **无** |
| `comments.nick` 与 `users.nick` 脱节（改过名）的情况 | **无** |

**真实价值**是另外两条：

1. **不受改名影响** —— `comments.nick` 是**发表时的快照**，用户改名后按旧昵称搜就找不到自己的评论；
   按内部 id 筛不受影响。
2. **少一步操作** —— 不必手打昵称去搜。

- 代码注释、UI 文案、测试说明都已按修正后的理由重写，**不再提"防重名"**。
- 测试也相应改成验"**改名后仍能找到**"（造一个改过昵称的账号），
  而不是原先那个"造两个同名账号"——后者根本建不出来（409）。

# 2026-10-09 追加：用户列表「只看管理员」筛选

## 新增

- 用户列表新增**角色筛选**（仅超管可见）：`全部角色 / 只看管理员`。
- `GET /api/admin/users?role=admin` → 只返回 `role >= 1`；未知值按**不筛**处理
  （与 `pageKind` 同一约定，多写一个键不会报错）。
- 服务端**不校验调用者角色**：谁能看用户列表谁就能看这份名单（普通管理员本也该知道有哪些同事）；
  改角色才是超管专属。前端对他隐藏筛选是因为"点了没用的选项只会让人困惑"。

## 设计取舍

| 决定 | 理由 |
| --- | --- |
| 只给"看管理员"一个方向，不做 `role=0/1/2` 逐档筛 | 实际需求是"我有哪些同事、权限对不对"；普通用户是绝大多数，按他们筛等于没筛（那本来就是默认视图） |
| 前端**隐藏**而非禁用 | 普通管理员没有可做的操作，给了也是干扰 |

## 测试过程中发现的两条**弱断言**（都是自己的测试写错）

| 现象 | 根因 | 改法 |
| --- | --- | --- |

| `默认播种了 4 条` 翻红（实际 3） | 断言了**绝对条数**，而这份清单可被前面的 UI 测试改动 | 该断言由 `tests/migration/rehearse.mjs` 在干净库上守；API 测试只验"返回结构正确"，不再依赖前置状态 |
