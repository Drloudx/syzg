# 2026-09-27 开发汇总

> 主题：打开速度优化。按实测字节数排序处理冷启动开销，并查清"线上缓存头与 `_headers` 不一致"的成因层面。

## 数据与解析

### 字体子集化（最大单项：8.28 MB → 0.93 MB）

- **实测背景**：`public/fonts/HarmonyOS_Sans_SC_{Regular,Bold}.woff2` 是 CJK 全字集（各 29063 字形），分别 4179.1 KB / 4300.6 KB。冷启动一次访问 `/`（重定向到 `/items`）的传输量构成：字体 **8.28 MB**、应用壳 JS 139 KB(br)、壳 CSS 23 KB(br)、`items.json` 193 KB(br)、首屏图标约 200 KB —— **字体占 94%**。字体浏览器缓存 7 天，所以老用户感觉不到、新用户极慢。
- **字符集现算**：新增 `scripts/dev/font-subset-lib.mjs`，从**随包发布的**输入算字符集（`public/data/**/*.json` + `src/**/*.{vue,js,css}` + `index.html`，共扫 1870 个文件）：内容 3713 个唯一字符（3523 个 CJK），补齐 ASCII/标点/全角后 4183 个。
- **新增** `scripts/dev/subset-fonts.mjs`（默认预览 / `--apply` 才写 / `--check` 纯 Node 供验收）。实测结果：

  | | 全字集 | 子集 | 省 |
  | --- | --- | --- | --- |
  | Regular | 4179.1 KB | **472.9 KB** | 88.7% |
  | Bold | 4300.6 KB | **478.8 KB** | 88.9% |
  | 合计 | 8.28 MB | **0.93 MB** | **88.8%** |

- **不丢字的保证**：生成时逐字自校验（子集 cmap 必须覆盖全部内容字符，缺失即报错且不写清单）。另有 18 个符号（`⌘ 🠔 ✓ ► ▾ ✦ 📜 ▶ ❤` 等）**源字体本来就没有**，今天也已经回退设备字体，子集化没有新增任何损失。
- **防回归**：`scripts/dev/verify.mjs` 新增断言"字体子集覆盖当前全部字符"。它比对"当前数据算出的字符集 sha256"与 `public/fonts/font-subset.json` 里记录的清单；数据更新后忘了重新子集化会**直接失败**，而不是静默回退系统字体。已用注入生僻字（`龘龗鱻爨`）实测确认会失败、移除后恢复通过。
- `@font-face` 改为子集优先、全字集作第二顺位 src 兜底（`src` 列表按 format 只择一，正常只下子集）。**注意 src 内部不做缺字回退**，缺字由 `--font-ui` 后面的设备字体接住。

### 图片版本表按目录分组（首屏 chunk raw 减 77 KiB）

- `__IMAGE_VERSIONS__` 会内联进**每个页面都 modulepreload** 的 `ui-*.js`。实测该表在该 chunk 里占 **29.0 KiB brotli（占该 chunk 64%）**——原始 175.8 KiB 里有相当部分是 brotli 压得掉的重复目录前缀。
- 改为按目录分组（键 `<目录>/<文件名>`）+ 哈希取 8 位十六进制：raw **175.8 → 95.7 KiB**，独立 brotli 28.6 → 21.6 KiB。
- **发现并纠正自己的一个测量错误**：第一次用 PowerShell 内联 `node -e` 测量时 `replaceAll('\\\\','/')` 转义写错，路径分隔符没换成 `/`，导致"按目录分组"的文件全落进同一个桶，得出"分组只省 24 KB"的错误结论。改用 write 工具落盘 `scratch/_measure-map.mjs` 后得到正确值（省 68 KiB）。教训：测量脚本也要避免 shell 转义，结论要复核。
- **碰撞判定的重要修正**：8 位哈希首轮构建就撞了 6 组，但核对后发现**全部是逐字节相同的重复素材**（`plants/lanlucao_1.webp` 与 `plants/shuiluguo_1.webp` 内容完全相同，多对同类）。同一路径的缓存键各自独立，共享版本串无害，所以判定必须用**完整 SHA-256**：只有"短哈希相同且内容不同"才是真碰撞。改为完整哈希比对后构建通过，且真碰撞会在构建期直接报错。

### 内联首屏那组数据的哈希 + 其余 manifest 按页面意图预热（去掉串行 RTT）

- `resourceClient.expectedHashFor()` 原先必须先读 `assets/data-manifests/<目录>-*.json` 才知道该文件的 sha256，才能拼出 `?v=<sha256>`。于是关键路径是 `壳 → manifest（1 RTT）→ 数据（1 RTT）`，落地页要白等一个来回才开始下载大文件。
- `vite.config.js` 新增 `INLINE_HASH_DIRECTORIES = ['data/parsed/']`（34 条，注入 3.2 KB），把首屏那组的哈希直接内联进 bundle。
- **只内联这一组**：`data/parsed/dungeons/`、`data/parsed/stages/`、`data/dialogs/`、`data/taskDialogs/` 都只在用户**点开某个详情**时才取；实测把它们一起内联会让内联表变成 194 条 / 18.9 KB，正好把上面版本表省下的 brotli 全部吃掉（都在同一个 chunk）。
- **其余 manifest 改为按页面意图预热**（新增 `prefetchResourceManifest()`）：页面挂载时先发起该目录的 manifest 请求，把这个往返藏进用户浏览列表的时间，点开详情时直接发数据请求。四个调用点：
  | 页面 | 预热目录 | 覆盖的按需请求 |
  | --- | --- | --- |
  | `DungeonsView` | `data/parsed/dungeons/` | 副本关卡详情 |
  | `ChaptersView` | `data/parsed/stages/` | 关卡详情 |
  | `TasksView` | `data/taskDialogs/` | 任务剧情正文 |
  | `HeroStoryPanels`（角色详情） | `data/dialogs/` | 角色档案/互动剧情正文 |
- **刻意不在启动时预取全部 manifest**：`data/dialogs/`(50.7 KB) 与 `data/taskDialogs/`(97 KB) 合计 148 KB，冷启动未必用到；按页面意图预热才能既不浪费字节、又藏掉 RTT。预热失败静默且不缓存（条目已从缓存移除，真实请求会重试），三点都有单测锁住。
- 合起来：首屏 `ui-*.js` **raw 229.8 → 152.7 KiB、brotli 45.6 → 39.8 KiB**，落地页去掉 1 个串行 RTT，另外三个「点开详情」路径的 manifest 往返也被藏掉。

### 角色突破材料核对：`items.json` 是白下的

- 角色详情原先无条件 `fetchItemData()`（本地 brotli 约 126 KiB）来解析突破材料的名称与图标。
- 按原表核对：`raw/consume.json` 全表 983 条里 **795 条带 items**（表结构本身支持），但 `heroRank` 引用的 **54 个 consume 条目全部只有 `money`、没有 items**。也就是说 `calculateUpgradeCosts` 的 `breakthroughItems` 恒为空，那次加载解析不出任何东西。
- 处理：`heroParser.js` 新增 `breakthroughConsumesItems(heroRankConfig, consumeDatas, rarity, job)`，`HeroesView` 只在"真的带材料"时才 `loadItemsOnce()`。**不删代码、不改数据契约**：配置以后加了材料，条件自然为真，行为与原先完全一致。新增 `tests/unit/hero-breakthrough.test.mjs`（4 项）锁住"当前原表下全为 false"与"一旦有材料立刻为 true"两个方向。

## 冷启动实测：真正的瓶颈是那张 1 MB 的地图底图，不是数据表

此前几轮的性能结论都建立在"文件体积 + brotli 估算"上，而本轮已经因测量口径错过一次，所以补了一次**浏览器冷缓存实测**：自起静态服务器（brotli + 按 `_headers` 意图给缓存头），用系统 Chrome 冷 context 打开页面，记录每个请求的真实字节。

首屏 `/`（→ `/items`）冷启动合计 **2857.9 KiB**（压缩底图与删图之前；最终值见下）：

| 请求 | 字节 | 占比 |
| --- | --- | --- |
| **`/ui/map_w1_bg.webp`（全局 `html,body` 背景）** | **1000.4 KiB** | **35.0%** |
| 字体（子集两枚） | 951.7 KiB | 33.3% |
| 物品图标 | 338.3 KiB | 11.8% |
| JS | 252.8 KiB | 8.8% |
| `items.json` | 126.0 KiB | 4.4% |
| CSS | 51.7 KiB | 1.8% |

- **P0 得到端到端确认**：冷启动只请求 `HarmonyOS_Sans_SC_{Regular,Bold}.subset.woff2`（472.9 + 478.8 KiB），**全字集请求 0 个**。这条必须用浏览器验证——本项目有前科：2026-09-18 记录过"WOFF2 只生成没改 `@font-face`，线上实际加载的仍是 TTF，而当时声称的'浏览器只下载 woff2'是错误结论"。
- **缓存策略本身是好的**：同 context 二次导航仅 3.4 KiB（复用 99.9%），说明 `?v=` 内容寻址 + `_headers` 长缓存的设计成立，成本只在新用户首次。
- **新发现：`map_w1_bg.webp` 是单页最大开销**，1000.4 KiB（1873×840），而它只是 `html,body` 的背景底图，**每个路由都要下**。
  - 尺寸本身**不算超标**：CSS 把它渲染在 `max(100vw, 100dvh × 2.2297619)` 宽，1440×900 下要 2007px、1920×1080 下要 2408px，都**大于**原图 1873px——也就是说它是被**放大**显示的，不存在"缩图无损瘦身"的空间。要省只能重新压缩（降低画质），而 SPEC §六 明确"仅在用户明确要求压缩时执行压缩"，所以本轮**没有动它**。
  - `/gacha` 也照下这 1000.4 KiB，而招募页用 `GachaStage` 铺了自己的整屏背板。同页截图两次（第二次注入 `background-image:none`）在 1440×900 下逐像素比对：**最大单通道差值 0、差异像素 0 / 1296000**——地图在 `/gacha` 上被**完全**盖住，那 1 MB 是纯浪费。
  - **尝试过用 CSS 跳过它，实测失败并已回退**（详见下节"被实测否掉的方案"）。
- 另一处死重量：`public/ui/test_map_w1_bg.webp`（**1151.0 KB**）在全仓库**无任何引用**（只有 `.gitignore:58` 与 2026-09-18 日志提到它的 `.png` 同名兄弟被列为"未使用的重复地图资源"；`.webp` 这枚一直留在库里并随每次部署上传 CDN）。**已按用户授权删除**，见下节。

### 被实测否掉的方案：用 CSS 让 `/gacha` 不下地图底图

记录全过程，避免以后有人再试一遍：

1. 先写 `html:has(.app-container.is-gacha-stage) { background-image: none }` → **仍下载**。
2. 探针确认不是选择器问题：挂载后 `document.documentElement.matches(':has(.app-container.is-gacha-stage)')` 为 `true`、`html/body` 计算值都是 `none`，但图片照样被请求 → 判断是"Vue 挂载前就开始了"。
3. 于是把类改成由 `index.html` 的**内联脚本在样式表之前**打到 `<html>`（并加 `App.vue` 的 watch 同步站内切换）→ **仍然下载**。
4. 再用探针量时间线：`is-gacha-route` 类**确实存在**、计算值**确实** `none`，而 map 资源的 `initiatorType` 是 **`css`**、`startTime` 781ms（早于 DOMContentLoaded 840ms）。

结论：**Chrome 的 CSS 背景图预加载扫描器不考虑层叠优先级**——它按样式表里出现的 URL 提前发请求，根本不知道某条声明最终会输给别的选择器。所以只要那张图的 URL 出现在**任何一份会被加载的 CSS** 里，`/gacha` 就会下它。唯一能真正避免的做法是把背景改成由 JS 挂载后再设置（`html.style.backgroundImage=...`），代价是**所有其他路由**的地图背景都变成"JS 执行后才出现"（现在 `html,body` 还有 `background-color:#000`，会先闪一下黑底）——为了一个路由省 1 MB 而让另外 19 个路由的观感变差，不划算。

**该方案已完整回退**：`index.html`、`src/App.vue` 与 HEAD 完全一致，`theme.css` 只剩 P0 的字体的改动（`git diff --stat` 已核对）。

### 第 3 轮补充的两项验证（都是"防静默失效"）

1. **子集缺失时会优雅回退、但优化会静默消失**——把 `dist/fonts/*.subset.woff2` 移走后实测：字体请求变成全字集（8480.4 KiB，占该次加载 88%），页面照常显示。也就是说**万一子集没被提交上去，站点不会坏，只是白优化**，而且不会有人发现。这正是 2026-09-18 那个坑的形状（"WOFF2 只生成、`@font-face` 没改，线上实际加载全字集，而'浏览器只下载 woff2'的错误结论一直没人发现"）。

### 用户配合排查 EdgeOne 的完整过程（结论：控制台里没有可改的开关）

用户提供了控制台截图与规则引擎 JSON，逐项排除如下。**新增三条硬证据**：

1. **源站是干净的（一刀切开源站与 CDN）**：`myrzg.pages.dev` 就是 Cloudflare Pages 源站，它对本例图片返回 **`public, max-age=604800`**（正确）。而自定义域名返回 `max-age=3600`。所以 `public/_headers` 完全正常，改写发生在它前面那一层。

## 字体 URL 补内容哈希（方案 B）：重新子集化后立刻生效

**起因**：用户问"以后加新内容会不会覆盖不到"。先答清这一点，再修了随之暴露的一个缓存问题。

**关于"会不会漏字"（结论：不会静默漏，最坏是个别字换字体）**：

- 有构建期断言。实测往数据里塞 `龘龗鱻爨犇骉羴` → `--check` 立刻失败并提示

  取决于提交前有没有按项目规范跑 `verify`。

  **源字体本来就没有**，它们用在 11 处 UI 里（`HeroesView` 技能展开箭头、`UiCollectionToggle`

  > Chrome 的 `check()` 不校验字形覆盖，而 CJK 字形在几乎所有中文字体里都是全宽、宽度区分不出来。

## 顶栏底部线改为棕色描边；查清 QQ 内置浏览器的顶部空隙

**改动**（用户要求）：`.app-header` 的 `border-bottom` 由 `3px var(--accent-bright)`（湖青强调线）
改为 `2px var(--border-color)`（棕色描边）。用户给出的那 6 条里其余 5 条**本来就已经是同样的值**
（`background-color` / `z-index` / `padding-top` / `box-shadow` / `flex-shrink`），所以实际只改了
这一条；`box-shadow` 顺手从 `rgba(0,0,0,0.5)` 换成等价的 `#00000080`（与线上压缩产物写法一致）。
用户应该是从线上压缩后的 CSS 里读到那段并贴过来的。

**QQ 顶部空隙的成因（已复现，不是推断）**：用户在 QQ 内置浏览器打开时，顶栏上方多出一条**木色空带**
（微信 / Chrome 没有）。把 QQ 与微信截图顶部裁出、放大 3 倍对比，确认那条带子**是 header 自己的
`background-color`（`#2b1f15`）**，不是"露出了页面背景"。

用 CDP 的 `Emulation.setSafeAreaInsetsOverride` 注入 `top: 40px` 的 safe-area inset 复现：

| | `--safe-top` | `padding-top` | header 高度 | logo top |
| --- | --- | --- | --- | --- |
| 无 inset（≈微信/Chrome） | `max(0px, 0px)` | `0px` | 101px | 10px |
| 注入 40px（≈QQ） | `max(40px, 0px)` | `40px` | **141px** | **50px** |

截图与 QQ 那张**完全一致**。结论：`.app-header { padding-top: var(--safe-top) }` 在
`env(safe-area-inset-top)` 非零时会撑出一条空带；**QQ 的 WebView 报了这个非零值**
（它把 WebView 铺到状态栏下方，同时又画了自己的标题栏，于是两边各让一次），微信与 Chrome 报 0，
所以只有 QQ 有。**注意：用户要求补的那条 `background-color` 并不能消掉它**——背景本来就有，
带子一直是木色的。

**修法（用户确认后按 B 的加强版实施）**：用户指出"QQ/微信都会自己补上那一块（宿主标题栏），所以你说的代价不会发生"——这个判断是对的，而且我又查到一个更硬的事实：

```java
// android/app/src/main/java/.../MainActivity.java
WindowCompat.setDecorFitsSystemWindows(getWindow(), true);   // true = 不 edge-to-edge
```

`targetSdk 36`（API 35+ 本会**强制** edge-to-edge），但原生壳**主动贴合系统栏** → **APK 里 `env(safe-area-inset-top)` 本来就是 0**，`padding-top: var(--safe-top)` 一直是 0、从没起作用。也就是说这个变量目前**只在 QQ 这类内置浏览器里真的非零**。代价比原先描述的更小。

关键实现点：**`--safe-top` 是全局布局变量**（顶栏内边距、吸顶偏移、弹窗内边距与高度、body 背景位置等十余处共用，见 `theme.css` / `App.vue` / `NavigationMenu.vue` / `UiModal.vue` / `RewardsView.vue`），所以判定做在**变量这一层**，而不是只改顶栏的 padding——否则那十余处仍按 `header + safe-top` 计算，40px 会从顶栏挪到弹窗/吸顶元素上。

```css
:root { --safe-top: 0px; }                       /* 默认：宿主已有标题栏 */
@media (display-mode: standalone), (display-mode: fullscreen), (display-mode: minimal-ui) {
  :root { --safe-top: max(env(safe-area-inset-top), 0px); }   /* 已安装 PWA */
}
html:has(.app-container.is-native-shell) { --safe-top: max(env(safe-area-inset-top), 0px); }  /* 原生壳兜底 */
```

**验证**（本地构建 + CDP 注入 `top: 40px` inset）：

| 场景 | `--safe-top` | `padding-top` | header 高 |
| --- | --- | --- | --- |
| 基准（无 inset） | 0px | 0px | 100 |
| ① 普通浏览器 + inset 40（≈QQ/微信宿主） | **0px** | **0px** | **100**（空带消失 ✅） |
| ② standalone + inset 40（≈已安装 PWA） | — | — | **CDP 不支持模拟 `display-mode`**（`matchMedia` 恒为 false），无法在此验证 |
| ③ `.is-native-shell` + inset 40（原生壳） | `max(40px,0px)` | 40px | 140（兜底有效 ✅） |

②的机制已被③证明（同一套"在沉浸式上下文覆盖 `--safe-top`"），产物 CSS 里也确认含该媒体查询；未能端到端验证的原因是**测试工具限制**，已在 `UI_COMPONENT_LIBRARY §1.5` 与本节如实标注。

**对现有环境零行为变化**：`--safe-top` 原本在这些环境里就求值为 0（原生壳/普通浏览器/微信），所以这次改动只去掉 QQ 那条多余空带。

## 补齐 `dvh` 的 `vh` 兜底（旧内核防退化）

**背景**：有朋友在 QQ 内置浏览器里反馈"页面特别卡、还没加载完快速操作就卡死不动"，但用户与另一位朋友同样用 QQ 打开都正常 → 指向**设备/内核差异**。排查中顺带扫出一个真隐患。

**先排除的（都有对照实验，不是推断）**：

| 假设 | 对照结果 |
| --- | --- |
| 图片加载导致 | ❌ **拦截全部图片后反而更卡**：长任务 2480 → **2881ms**，帧 p95 83 → 117ms |
| `background-attachment: fixed` | ❌ 关掉 2372 → 2354ms，p95 不变 |
| `backdrop-filter: blur()` | ❌ 关掉反而 ↑126ms（噪声） |

**量到的真实成本**（393×852 / CPU×4 / 快速 4G / 3 秒滚 24000px）：长任务 **28 次 / 2372ms**、帧 p95 83ms、最大帧 183ms；CPU Profiler 排行单函数 `dn`(ui-*.js) 1251ms、(program) 1842ms。即主线程在滚动窗口里被占了近 80%——**强机无感、弱机卡死，属阈值效应**。注：这是刻意压到极端的测试，比正常浏览激进得多。

**本次改动（用户选的 A 项）**：全仓扫出 **17 条"只有 `dvh`、没有 `vh` 兜底"** 的声明——`dvh` 需要 Chromium 108+，旧 WebView 解析到未知单位会整条丢弃，于是高度/尺寸约束消失。两类处理方式不同：

- **15 条普通属性**：在前面补一条同属性的 `vh` 声明（旧内核丢弃 `dvh` 那条，`vh` 生效）。涉及 `App.vue` 8 条（全在 `@media (min-width:1025px)` 桌面分支）、`UiModal.vue` 3 条、`FurnitureView.vue` 与 `RewardsView.vue` 各 1 条。
- **2 条自定义属性**（`theme.css` 的 `--page-bg-width/height`）：**不能靠写两遍兜底**——CSS 自定义属性对未知单位不做解析校验，两份值都会留下、到 `var()` 使用处才整条失效，后果是 `background-size` 作废、**地图背景退回平铺**。改为「默认给 `vh` 值 + `@supports (height: 100dvh)` 里给 `dvh` 值」。
  > 顺带纠正自己：第一版审计脚本把行号报成了规则的右花括号（不是声明行），按它改全落空；第二版改按内容扫描才成功。

**验收**：审计脚本复测 **0 条风险**（20 条已兜底，含 2 条 `@supports` 保护的）；构建产物含 `@supports (height: 100dvh)` 覆盖；真实浏览器读计算值仍是 `max(100vw, calc(100dvh * 2.22976))` → **现代浏览器无回归**；`npm run verify` 退出 0；单测 158/158。

**诚实的边界**：这是**防御性修复**，**不保证治好那位朋友的卡顿**——他那台设备的具体原因（内核版本 / 弱机）尚未确认。已请他试"更新 Android 系统 WebView / 换 Chrome 对比"。真正的治本方向是降低每帧主线程开销（先用 dev 构建 profile 出那个 1251ms 的函数是谁）。

### 追加：上面的"写两遍"方案到不了线上，已改为变量集中判定

改完做**产物级复核**时发现：压缩产物里 `html,body{…height:100dvh;…}` —— **我加的 `height:100vh` 被删掉了**。查证与修正过程：

1. **确认是压缩器干的**：把 `build.cssMinify` 设为 `false` 重新构建，`height:100vh;height:100dvh` **两条都在**；恢复压缩后前一条消失。即压缩器把"同属性后一条覆盖前一条"当重复声明清理，而它并不知道 `dvh` 在旧内核上不受支持 → **兜底到不了线上**。
2. **试 `build.cssTarget`（设为 dvh 之前的版本）**：能让兜底部分存活，但 15 条里只活下来约一半（`100vh` 出现次数 12 → 19），CSS 从 334.8 → 342.4 KiB（+2.3%），首屏 CSS 117.9 → 123.3 KiB。`css.lightningcss.targets` 无效（说明是 esbuild 那条链路）。**不划算，放弃。**
3. **改用"一处判定、处处引用"**：`theme.css` 定义 `:root{--vh100:100vh}` + `@supports (height:100dvh){:root{--vh100:100dvh}}`，全仓 21 处 `dvh` 改为 `var(--vh100)`（`30dvh` 写成 `calc(var(--vh100) * 0.3)`），并删掉之前加的那 18 条 `vh` 孪生。每个位置只剩**一条**声明，压缩器无从下手。
   - 踩到的坑：转换脚本把 `@supports` 的**条件**也一起替换成了 `var(--vh100)` —— 而 `@supports` 条件里**不能用 `var()`**（非法，整块会被丢弃）。已改回字面量并在文档里写明。
   - 踩到的第二个坑：`--page-bg-*` 的**基础声明**写的是 `100vh`（不是 `dvh`），所以转换只动了那段 `@supports`；删掉该块后地图背景**永久停在 `100vh`**、丢掉动态视口行为（浏览器实测 `--page-bg-width` 计算值为 `100vh` 时发现）。已改为 `calc(var(--vh100) * 2.2297619)` 等。
4. **验收**：
   - 产物里字面量 `100dvh` **只剩 2 处**（`@supports` 的条件与覆盖值），`var(--vh100)` 18 处 → 没有可被当作重复声明清理的东西了。
   - 真实浏览器计算值：`--vh100` / `--page-bg-width` / `--page-bg-height` **全部为 `100dvh`**（现代内核无回归），`background-size` 2006.78×900、`.app-container` 高 = 视口高。
   - **模拟旧内核**（强制 `:root{--vh100:100vh}`）：`.app-container` 高仍为 852、网格可视高 474 / 内容高 14702、只渲染 8 张卡片 → 布局与虚拟化行为**完全一致**，没有退化成"渲染全部卡片"。
   - `npm run verify` 退出 0；单测 158/158。

## 滚动热路径：把"动作路径"的函数挪出去（并按实测修正结论）

**起因**：查"朋友在 QQ 里卡"的治本方向——先用 CDP Profiler 定位滚动期间最耗时的函数。

**定位过程（都靠数据，不靠猜）**：

1. 线上产物剖析：`dn @ ui-*.js` 自耗时 **895ms**，是所有 JS 函数第一名，且是**叶子函数**（无子调用），调用链 `dn ← fn ← i`。
2. 压缩代码只有一行，用剖析给出的**列号**（110186）直接切片出函数体，认出：
   `dn` = `isScrollableElement`、`fn` = `resolveScrollTarget`（`src/utils/scrollTarget.js`）。
3. 调用者：`UiBackToTop.vue`（约 20 处使用）与 `useLazyList.js`（11 个页面），**两处都在每帧的滚动处理器里调用**。
4. 精确计量（包装 `Element.prototype` 的几何 getter + `getComputedStyle` 分别计时）：
   **`scrollHeight` 60 次 / 731~764ms（单次平均 13.7ms、最高 46ms）= 窗口的 13.1~13.3%**；
   而 `getComputedStyle` 只花 **2ms** —— **我最初的猜测（样式计算）是错的，真凶是强制同步布局**。

**改动（按"最适合长期维护"的方向，用户选择）**：不做缓存，而是**把两种路径显式分开**——

- `scrollTarget.js` 新增 `resolveScrollRootFromEvent(event, preferred)` 与 `getScrollTop(target)`，并写明**热路径禁用** `resolveScrollTarget`/`getScrollMetrics`。
  理由：缓存方案引入"需要失效的缓存状态"（列表数据加载后才变可滚、弹窗开合都会让它过期），那正是长期 bug 温床；而**滚动事件的 `target` 本身就是滚动元素**，比较即可、无状态。
- `UiBackToTop` 改用热路径 API（并去掉 `getScrollMetrics` —— 它连用不到的 `scrollHeight` 一起读，是第 2 次强制布局）。
- `useLazyList` 改用热路径 API，并去掉 `scopedContainer.offsetParent === null` 判断（同样强制布局；事件既然从该容器冒上来，它必然可见）。
- **护栏**：`resolveScrollTarget` 开发期统计调用频率，1 秒超 30 次即 `console.warn` 指回规则；新增 `tests/unit/scroll-target.test.mjs`，用**读了就抛错的几何 getter**把"热路径不许读几何属性"钉死（8 项）。
- 复核：剩下 8 处 `resolveScrollTarget` 调用点逐个确认都在冷路径（`findRequestedDropTarget` / `loadData` / `goPrerequisite` / `openItem` / `scrollToTop` / watch 回调等）。

**验收**：
- 强制布局：`scrollHeight` **60 次 / 731~764ms（13.1~13.3%）→ 0 次 / 0ms（0.0%）**。
- **但滚动长任务没有改善**：2277~2321ms（40.5~40.7%）→ **2339~2358ms（41.1%）**，帧 p95 83ms 不变。
  **结论：强制布局是"把本来就要做的布局提前"，不是额外工作，总量不变。**所以这次改动的价值在**结构**（消除一个开销随实例数增长的陷阱、语义明确、有测试守住），**不是**已量到的提速——不把它说成性能优化。
- `npm run verify` 退出 0；单测 **166/166**（+8）。

**顺带查清"真正的大头"**（CDP `Performance.getMetrics`，滚动窗口 9730ms）：
`TaskDuration` 3899ms，其中 **JS 仅 86ms（2.2%）**、布局 484ms（12.4%）、样式重算 487ms（12.5%），
**其余约 73% 是绘制/合成/光栅化/图片解码**；同时 60 步滚动里 **DOM 节点净增 5780 个**。
→ 滚动卡顿的主因是**虚拟列表的 DOM 增删与随之而来的渲染量**，继续优化 JS 收益很小。
下一步方向应放在 overscan、卡片 DOM 体积与图片解码上（待用户确认后再动）。
