## 1. 移动端贴边二合一悬浮拉手（`EdgeFloatingWidget`）

### 1.1 背景与问题演进
- **重叠遮挡痛点**：在移动端打开物品详情等弹窗后，底部的评论发表区（富文本输入框 + 发送按钮）紧贴底部，与右下角全局悬浮的「功能导航」汉堡按钮以及「回到顶部」圆钮发生物理遮挡，输入和点击极易误触；
- **排查并放弃的过渡方案**：
  - *输入框 sticky 吸底*：占用了手机屏幕 1/3 的黄金可视区域，装备与图鉴正文严重受限，且割裂羊皮纸弹窗视觉；
  - *底部极窄胶囊条 + 嵌套抽屉*：交互层级过深，点击发表需要再弹一层窗口，操作链路繁琐；
- **最终落地方案**：用户构想并敲定的**贴边吸附二合一拉手（方案 A）**。

### 1.2 结构与交互实现
- **收起态**：贴边极简小拉手（22×52px，原木质感，三道小抓手防滑纹与指示箭头），紧贴屏幕边缘，不占视口内容；
- **展开态**：无缝一体化原木胶囊外壳（`.edge-widget-capsule`），展开时拉手作为右/左端封口，平滑伸出「顶部」与「导航」两枚独立操作按钮，彻底消除分裂缝隙；
- **自由拖拽与持久化**：
  - 垂直方向通过 pointer 事件支持单指/鼠标自由拖动，松手自动避开顶栏（80px）与底栏安全区（80px）；
  - 自动通过 `localStorage` 记住上次位置；
  - 水平方向跨越屏幕中线（35%~65%）自动磁吸换边到左/右侧屏缘；
- **全局整合**：
  - `UiBackToTop.vue`：在移动端媒体查询（`<= 1024px`）下设置 `display: none !important`，桌面端保持原固定圆钮；
  - `App.vue`：挂载 `EdgeFloatingWidget`，移动端隐藏原 `nav-fab-btn`，统一由拉手挂件承接。

### 1.3 移动端全场景智能寻迹置顶
- **踩坑排查**：初版调用 `resolveScrollTarget()` 未传参，兜底返回了 `window` 并执行 `window.scrollTo`。在移动端，主页面长列表由带有 `[data-main-scroll]` 属性的内部容器（`.ui-card-grid-scroll` / `#itemsGridScroll`）独立滚动，`window` 滚动偏移本就是 0，导致点击「顶部」毫无响应。
- **重构寻迹策略（`onBackToTopClick`）**：
  1. **前台弹窗**：若当前打开了 `UiModal`（如物品详情），优先定位其最上层 `.ui-modal-body` 滚动置顶；
  2. **主页面状态**：精准遍历当前页内可见的 `[data-main-scroll]`、`.ui-card-grid-scroll` 核心滚动容器执行 `scrollTo({ top: 0, behavior: 'smooth' })`；
  3. **桌面端与全局**：兜底滚动 `.app-container` 与 `window`。

## 2. 长列表快滑感知与图片请求防挤占调度（Fast-scroll Throttle）

### 2.1 现象与根因剖析
- **现象**：在物品图鉴全量无筛选状态下，手机端用力快速向下滑动长距离并停下时，停下的区域图片迟迟不显示，反而像是在“从头开始一张张往后慢慢加载”。
- **根因**：
  1. 物品数据（`items.json`）在初始化时已全部加载进本地内存，但视图层采用 `@tanstack/vue-virtual` 虚拟网格（`UiVirtualGrid`）；
  2. 惯性飞速划动过程中逐帧快速挂载新行；每张卡片自带 `<img loading="lazy" src="...">`，浏览器在 1~2 秒内瞬间收到上百张新图片的下载请求，塞爆了 HTTP/2 连接并发池（实测禁用缓存峰值 450+ 个）；
  3. 当手指停在目标区域时，当前视口图片的请求排在网络队列的最末端，必须等待飞速划过的那几百张废弃图片排队传输，产生“从头慢慢加载”的排队感。

### 2.2 主流解决方案落地
采用工业级大型电商/图鉴类应用的**“滚动停顿优先加载（Scroll-Idle Priority Loading）”**策略：

1. **快滑状态实时感知（`UiCardGrid.vue`）**：
   - 监听捕获阶段滚动事件，基于位移差与时间差（$\Delta y / \Delta t$）计算即时滚动速度；
   - 速度阈值设为 `0.8px/ms`（约 `800px/s`），超过即判定为“飞速划过”，开启 `isFastScrolling = true` 并向下 `provide`；
   - 监听现代手机浏览器的原生 `scrollend` 事件，配合 `120ms` 空闲防抖计时器，手指停顿或惯性滑动结束的瞬间立刻解除快滑状态。
2. **图片并发防挤占调度（`UiItemCard.vue`）**：
   - 维护会话级内存缓存 `window.__loadedUiItemImages = new Set()`；
   - **已看过的图片**：无论划动速度多快，直接秒出（0 延迟）；
   - **未看过的冷图片**：
     - 飞速划过期间暂不挂载 `<img>`，保留原生品质底框与名称；
     - 停顿或惯性停止后，当前视口内卡片立刻挂载 `<img>`，独享 100% 浏览器并发带宽，秒级渲染；
   - **平滑过渡**：配合 `0.15s` 轻度渐入（`opacity: 0 -> 1`），避免生硬跳变。

## 5. 账号体系：需求变更 + 平台约束实测（推翻了旧稿的关键数字）

用户把需求从"无密码邮箱验证码"改成 **注册用邮箱验证码 + 密码登录 + 改密码也要邮箱验证**，
即**必须有密码**。于是先重核"Workers 上到底能不能存密码"，结论与旧稿不同：

- 旧稿写"PBKDF2 600k 轮实测 **104ms**"——那是 **Node** 的数。**真实 workerd 里是 279ms**（慢 2.7 倍）。
- 更关键：生产对 KDF 是**入口封顶**（参数超了直接报错，不是跑慢）。
  `workerd/src/workerd/io/limit-enforcer.h`：`DEFAULT_MAX_PBKDF2_ITERATIONS = 100'000`、
  `DEFAULT_MAX_SCRYPT_COST = 1u << 20`（即 `N×r×p ≤ 1,048,576`）；
  Cloudflare 自己的注释写着这"**WAY below the recommended minimum iterations**"。
- 封顶**至今有效**：`cloudflare/workerd#1346`（2023-10-25 开，**仍 open**，最后活动 2026-09-20）里
  kentonv 说明"CPU 限流器无法中断 BoringSSL 的 PBKDF 循环，所以只能在入口按轮数封顶"，
  jasnell 说明"workerd 已解除默认上限，但**生产环境仍保留**"；2026-01-26 仍有开发者报告 210,000 轮报错。

实测（新增 `scripts/dev/kdf-probe/`，本地 `wrangler dev` 里跑，**不进构建 / verify**）：

| KDF | 参数 | workerd 实测 |
| --- | --- | --- |
| SHA-256 摘要（基线） | — | 0.005 ms |
| PBKDF2-SHA256 | 10,000 轮 | 4.4 ~ 4.8 ms |
| PBKDF2-SHA256 | 100,000 轮（**生产上限**） | 44.4 ~ 48.4 ms |
| scrypt | N=16384 r=8（16MB，cost 131072） | 27 ~ 30 ms |
| scrypt | N=32768 r=8（32MB，cost 262144） | 54 ~ 57 ms |

→ 免费版 10ms 只够约 **21,000 轮**（OWASP 推荐值的 1/28）；
付费版也被顶在 10 万轮（推荐值的 1/6）。

**方案重写要点**（`docs/technical/ACCOUNT_SYSTEM.md`）：

- 推荐 **客户端 KDF**：浏览器 / 手机跑 PBKDF2-SHA256 **600k 轮**，只把 256 位 `verifier` 发上去；
  服务端存 `HMAC(pepper, verifier)`（≈0.02ms）。**免费、强度达到推荐值**；
  且 pepper 不在 D1 → **D1 单独泄露不可爆破**（这一点比"服务端直接哈希密码"更强）。
- **刻意不做**挑战-响应 / SRP / OPAQUE：那要求服务端持有明文 `verifier` 当密钥，
  "库泄露也安全"这条就消失了，得不偿失。
- 盐用 `HMAC(SALT_SECRET, email)` 现算、**不入库** → 少一次 D1 读，
  且对不存在的邮箱也返回盐 → **不泄漏账号是否存在**。
- 备选路线 B（Workers Paid $5/月 + 服务端 scrypt N=2^14）也写清了，
  并标注风险："降级回免费版会让**所有登录** 1102 报错"，属停不掉的付费依赖。
- **发信通道结论变了**：Cloudflare 原生 `send_email` 绑定（Email Service）**用不了**——
  给任意收件人发信需 Workers Paid，且发信域名**必须是 Cloudflare 托管的 zone**；
  实测 `yxzmy.top` 的 NS 是 `peach/henry.dnspod.net`（**DNSPod**）。
  推荐仍走腾讯云 SES（记录加在 DNSPod，与现有 DNS 一致）。
- 顺带记下一个"邮箱 = 信任根"的真实权衡：改密码走邮箱验证码（用户指定），
  意味着**能读邮箱的人就能改密码**；缓解措施是"改完作废其它 session + 发变更通知邮件"。

## 6. 腾讯云 SES 落地步骤成文 + 两项前置实测

把"怎么配 SES"从一句话写成了**可照抄的六步清单**（方案 §7.3），并补上 §7.4 的
`SendEmail` 接口契约。过程中**替用户做了两项只读前置检查**：

**① 域名 DNS 冲突预检（实测 `yxzmy.top`）** —— 结果全空，可以放心加记录：

| 查的东西 | 结果 |
| --- | --- |
| `yxzmy.top` TXT（现存 SPF） | 无 |
| `yxzmy.top` MX | 无 |
| `_dmarc.yxzmy.top` TXT | 无 |
| `mail.yxzmy.top` TXT / MX | 无 |

且一个域名的 SPF **只能有一条**，子域可避免与根域将来打架）。

**② 复核了 SES 的产品约束**（官方文档，2026-10-05）：

- **只支持模板发信**（"默认仅支持使用模板发送邮件"，违规返回 `FailedOperation.WithOutPermission`）
  → 验证码必须**先建模板并过审**（官方说**1 个工作日**），**所以要提前发起**，不能等写完代码。
- 免费额度确认：**每账号 1000 封，不限有效期、用完为止**；超出 **0.0019 元/封**。
- **未见 ICP 备案要求**，只需腾讯云账号**实名认证**。
- 发信地址格式有坑：带别名时是 `别名 + 一个空格 + <邮箱>`，**别名里不能有冒号**。
- ⚠️ 记下**最大送达率风险**：`yxzmy.top` 是 `.top` 后缀，国内部分邮箱对其初始信誉偏低；
  若垃圾箱率高，退路是换 `.com`/`.cn` 域名专门发信。

**③ 当日实际配置结果（用户操作 + 我方独立 DNS 复核）**：

  `QcloudAccessForSESLinkedRoleInBilling`）——**只涉及账务计费、不需要交密钥、可撤销**，同意即可。

  → **调 `SendEmail` 时 `Region` 必须是 `ap-hongkong`**。

- **不要开「独立 IP」**（900 元/个/月 + 冻结 + 2~4 周预热；小量发信用它反而更差）。

### 8.1 真机实测的两个坑（2026-10-05 当晚踩到，都会重复踩）

**坑①：`http://<局域网IP>` 不是安全上下文 → `crypto.subtle` 根本不存在**

手机访问 `http://192.168.31.248:5173/scripts/dev/kdf-bench.html` 时页面报
「crypto.subtle 不可用」。**这不是设备问题，也不是方案问题**，而是浏览器的硬规则：

| 页面来源 | 是安全上下文吗 |
| --- | --- |
| `https://` 任意 | ✅ |
| `http://localhost` / `127.0.0.1` | ✅（浏览器特批） |
| **`http://192.168.x.x`（局域网 IP）** | ❌ **不是** |

→ 测量页必须落在**安全上下文**里。三种办法（已写进页面内置的提示卡）：

1. 在**电脑**上用 `http://localhost:5173` —— 只能测桌面；
2. 手机 **Chrome** 进 `chrome://flags/#unsafely-treat-insecure-origin-as-secure`，
   把该地址填进白名单 → Enabled → Relaunch；
3. 电脑 Chrome 开 `chrome://inspect` → Port forwarding → 手机访问 `localhost:5173`。

> 补充：**微信内置浏览器不行** —— 它是另一套 WebView（XWEB），
> 既进不了 `chrome://flags`，也不保证提供 `crypto.subtle`。**必须用 Chrome。**

**生产环境不受此限制**：网页是 `https://syzg.yxzmy.top`；
安卓 App 的 origin 是 `https://localhost`（`capacitor.config.json` 里 `androidScheme: "https"`）。
两者都是安全上下文。

**坑②：CDP 的 CPU 节流对原生 WebCrypto 无效 —— 桌面模拟不了低端机**

本想用 Chrome DevTools 协议的 `Emulation.setCPUThrottlingRate` 在桌面模拟慢设备。
实测结果：

| CPU 节流 | KDF 中位数 |
| --- | --- |
| 1×（不限速） | 154ms |
| 4× | 142ms |
| 6× | 118ms |
| 10× | 140ms |
| **20×** | **144ms** |

**20 倍节流下耗时几乎不变。** 原因：`crypto.subtle.deriveBits` 跑在
**BoringSSL 原生代码**里（不在 JS 主线程），而 CDP 节流只限制 **JS 执行速率**。

→ 两个推论：

1. **好消息**：这个计算**不依赖 JS 引擎性能**，只吃**原生 CPU 与 SHA-256 指令加速**
   （ARMv8 有 SHA-256 扩展）。所以低端机的放大倍数不会像纯 JS 那样夸张；
2. **现实**：**只能真机量**，桌面上模拟不出来 —— 不过这条当晚就解决了（见 8.2）。

### 8.2 真机实测：**404ms，600k 轮不需要降** ✅

| --- | --- |

### 9.2 端到端测试抓到的三个 bug（**单测全都发现不了**）

这三个都是"每个函数单独都对、连起来才错"的类型，值得单独记：

**① 域分隔：公开的盐会连带泄漏 `email_hash`**

方案原稿里 `email_hash` 与 `salt` 是同一个表达式。但 `/api/auth/salt` 是**公开接口**，
于是 `email_hash` 也被公开了 —— 万一 D1 备份泄露，攻击者能拿哈希清单逐个调该接口
反查"这些邮箱在不在库里"。修法是给 HMAC 加不同用途前缀（`'lookup:'` / `'salt:'`），**代价为零**。
单测专门守这一条。

**② 换邮箱时不给"新邮箱"发码 → 整个功能不可用**

发码逻辑原本是"非 `register` 用途且邮箱未注册就不发信"（为了不给陌生人发垃圾邮件）。
但**换邮箱的新邮箱通常尚未注册** —— 正好被这条规则掐死。
修法：只有 `password` 用途才做"未注册不发"，`email_change` 必须发。

**③ 🔴 换邮箱会让密码永久失效（最严重的一个）**

盐是按邮箱派生的（`salt = HMAC(SALT_SECRET,'salt:'+邮箱)`），而库里存的是**按旧盐**算的
`verifier_hash`。换完邮箱，盐变了 → 新算的 verifier 永远对不上 → **用户再也登不上**。

症状极具误导性：**密码明明是对的**，只有"换过邮箱"的账号会中招。

修法：把盐存进 `users.pw_salt`（盐不是秘密，本来就公开返回），换邮箱时不动它。

> **共同教训**：凡是"由 A 派生、但 A 会变"的东西，都要在 A 变之前固化下来。
> 另见方案 §4.2.1。

### 9.3 两个环境坑（都会重复踩，已做防护）

**① `wrangler pages dev` 没有 `--strictPort`，端口被占时**静默换端口继续跑

踩到的现象：一个几小时前启动的**僵尸 `workerd`** 占着 8788，于是新服务换了端口，
而所有探测都打在旧服务上 —— 表现为"代码明明改了、行为却没变"，**且没有任何报错**。

端口被占就**拒绝启动**并打印清理命令。宁可起不来，也不要"起来了但你没在测它"。

**为什么网格要换掉**：网格会留下**可记忆的规律** —— 人看几轮就能靠格子位置记形状，

### 10.4 背景图：按 URL 引用，**不内联**（这条很关键）

用户要求"用网站主背景图做背景图"。这张图是 `/ui/map_w1_bg.webp`，与
`src/assets/theme.css` 里 `html, body` 的背景**同一张**，**原图 251.7KB**。

**不能内联 base64**：膨胀到约 340KB，会让**每个**验证码请求凭空多出这么大一坨。

**但也不需要内联**：验证码 SVG 本来就必须**内联进 DOM**（`.hit` 热区要绑点击事件），
内联时相对 URL 按页面 origin 正常解析；而且站点别处早已加载过这张图，
**浏览器缓存直接命中，零额外传输**。

实测：**加背景前后 SVG 只从 79.5KB 变成 85.7KB**（+6KB 是颗粒/墨点/晕影那几层）。

> 代价：**不能把这个 SVG 塞进 `<img src="data:image/svg+xml,...">` 渲染** ——
> 那样外部引用会被拦掉，背景退化成兜底底色（**不报错，只是没图**，属于最难查的一类）。
> 已在代码注释里写明。

### 10.5 中途踩的坑："虚化"是我加的，不是图的问题

为了让蛋图在花哨的地图上有对比度，我在背景图上压了一层 `opacity=0.6` 的暖色薄纱。
用户看到截图后直接说"**不要虚化**"。

**修法**：**不加任何整幅半透明色块**，背景图什么样就什么样；
只保留颗粒（0.1）、墨点划痕、以及**只压边缘**的轻晕影（0.18）。
蛋图可读性改由"蛋图自身边缘清晰 + 地图底色本就是浅色羊皮纸"来保证。

**并加了永久守卫**（`🔴 背景图不许被整幅色块压住 / 不许模糊`）：
扫描背景图**之后**所有"铺满整幅 + 实色填充"的矩形，透明度不得 > 0.15，且不许有 `feGaussianBlur`。

> 教训：**"为了可读性调暗背景"这种改动，用户的第一感受往往是"你怎么把我的图弄糊了"。**
> 这类整幅覆盖式处理要极其克制，能靠局部（描边、投影）解决就别动全局。

### 11.2 一条必须守住的安全行为：封禁要"封得住"

**封禁如果只改 `users.status`、不清 `sessions`，用户手上那个 30 天的令牌还能继续用。**
这种"封了但没封住"是最糟的失败方式 —— 管理员以为处理完了，实际什么都没发生。

端到端套件里有一条专门守它：

```
✅ 封禁前该账号能访问 /api/auth/me
✅ PATCH 封禁 → 200
✅ 🔴 封禁后**原令牌立即失效**（否则就是"封了没封住"）
✅ 🔴 封禁后无法重新登录 → 403 且文案是「已被停用」
✅ 库里该用户会话已清空
```

还有一条容易写错的语义边界：**`PATCH` 不允许把状态改成 3（已注销）**。
注销是**用户自己的动作**，且要连带改写评论昵称；管理端要清账号请用 `DELETE`
（明确的"彻底删除"语义）。两者对邮箱的处理**相反**：

| | 用户自助注销（软删除） | 管理端彻底删除 |
| --- | --- | --- |
| `users` 行 | 保留，`status=3` | **删除** |
| 评论 | 保留，昵称改写「账号已注销」 | 同左，且 `user_id` 置空 |
| 邮箱 | **永久占用，不可再注册**（防冒用历史评论） | **释放，可重新注册** |

端到端里两条都验了（一条 `🔴 该邮箱不可被重新注册`、一条 `🔴 彻底删除后该邮箱可重新注册`）。

## 13. 真机走查抓出的两个真 bug（都只在真机上暴露）

这两个 bug **单测、端到端、Playwright 全都抓不到** ——
它们都要求"真浏览器 + 真登录 + 真触摸"这一整条链路。

### 13.1 `mine` 永远是 false：读评论没带令牌

`commentApi.js` 里 `postComment` / `deleteOwnComment` 都带了令牌，
**偏偏三个读函数（`fetchComments` / `fetchCommentReplies` / `fetchRecentComments`）没带**。

后果：服务端算 `mine` 时看不到会话 → 全 false → **登录用户永远看不到删除按钮**。

为什么端到端没发现：它是"直接用带 header 的请求"测接口的，
**接口没错，错在客户端没发这个 header**。教训 ——
**端到端测的是接口契约，测不出客户端有没有按契约调用。**

### 13.2 更隐蔽的那个：会话恢复与评论加载的竞态

补上令牌之后**仍然**没有删除按钮。真因是时序：

```
App 启动 ─┬─ restoreSession()   ← 刻意不 await（不阻塞首屏）
          └─ 评论列表 load()    ← 跑得更快，此刻 getToken() 还是空串
```

刷新也一样（列表先到、会话后到），所以**每次都是错的**，不是偶发。

修法：`authSession` 暴露 `whenSessionReady()`，`commentApi.request()`
**先 await 它再取令牌**，并规定调用方**不要**自己传 `token: getToken()`
（那正好绕开这个等待）。责任收到一处，不可能再漏。

> 这类"两个异步初始化谁先到"的问题，靠"多测几次"是发现不了的 ——
> 因为它每次都错，只是错得没有声音。

### 13.3 一个不是 bug 的"bug"

最后一版断言在讨论区列表里找「删除」按钮，一直找不到。
查到底才发现：`DiscussionsView` 给 `CommentsPanel` 传了 `read-only`
（**源码里本来就有**）—— 讨论区列表从来不显示删除按钮，
删除入口按设计在「我的评论」里（M5）。

**是我的断言错了，不是代码错了。** 断言改成了 M4 真正交付的东西：
服务端按会话正确标出 `mine`，且「我的评论」接口能按 `user_id` 查到（跨设备）。

### 13.4 真机自动化的四个坑（都已写进 `scripts/dev/phone-cdp.mjs` 的注释）

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| **手机息屏** | CDP 连接正常，`Runtime.evaluate` 永远超时 | Android 息屏会**冻结页面主线程**。`svc power stayon true` 在 MIUI 上不生效，得先 `KEYCODE_WAKEUP` |

| **开错页面** | 注册全过，但"身份条/编辑器/发布"三连失败 | 默认路由是 `#/items`，那里**没有评论框**；要显式开 `#/discussions` |
| **缓存参数位置** | 路由匹配不上、页面空白 | 哈希路由下 `#/discussions&t=123` 会被当成路径 `/discussions&t=123`；`?t=` 必须在 `#` **前面** |

## 14. M5：个人中心里的「我的评论」

### 14.1 做了什么

个人中心新增一行「我的评论」，进去是一条条自己的评论：

```
页面名（站内讨论区 / 物品 / 角色…）   状态标签   时间
正文（最多三行，点「去看看」看全文）
                        去看看   删除
```

| 能力 | 说明 |
| --- | --- |
| **列表** | `GET /api/auth/comments` 按 `user_id` 查，**换设备也看得到** |
| **状态** | `待审核` / `已隐藏` / 正常。**作者自己必须看得见**，否则会以为"发出去了但没了" |
| **删除** | 复用评论区那套（服务端按 `user_id` 判归属），删完**只从本地列表移除**，不整页重拉 |
| **去看看** | 跳到那条评论所在页面（关掉弹窗，否则用户看不到自己跳去了哪） |
| **加载更多** | 游标分页 |

**为什么"只从本地移除"**：用户可能已经翻了好几页，重拉会把这些页丢掉、
滚动位置也会跳。这一点在评论区那边就踩过（当时写在注释里了），这里沿用。

### 14.2 "跨设备"这件事终于成立

本机身份时代，「我发过的评论」靠**每台设备各自存的自删令牌** ——
换台手机登录同一账号，既看不到、也删不掉。现在归属在服务端，两边一致。

### 14.3 测试写法的两个坑（都让"跑一次绿、再跑一次红"）

**① 所有测试共用一个昵称常量**

`NICK` 是模块级常量，10 条测试共用 —— 而**昵称全站唯一**。
结果：谁先注册谁赢，其余卡在"昵称已被使用"，**挂哪两条取决于并行调度顺序**。

改成 `registerAccount()` 每次生成唯一昵称与邮箱并返回，
调用方用返回值断言。这类随机失败的测试比没有测试更糟。

**② 本地限流额度被自己耗光**

真机 + Playwright + 端到端一轮打了几百次请求，把 `.dev.vars` 里的
`RATE_LIMIT_PER_HOUR=200` / `RATE_LIMIT_PER_DAY=500` 打满，
于是**端到端全变 429**，看起来像大面积回归。

已把本地额度提到 100000。两个要点：

- `.dev.vars` 是 **wrangler 启动时读的**，改了必须**重启** API 才生效；
- 生产环境**不要**设这两个变量，用默认值（那条保护是给真实流量用的）。

### 15.3 🔴 一个很隐蔽的 Vue 坑：函数式 `:ref` 在卸载时也会被调用

第一版把四个发码入口共用**一个**弹窗，用 computed 挑：

```html
<CaptchaDialog
  v-if="activeCode"
  :ref="(el) => (activeCode.captchaRef.value = el)"
/>
```

`activeCode` 可能返回 `null`。而 **`:ref` 的函数形式在组件卸载时也会被调用（传 `null`）** ——
那一刻 computed 已经变成 `null`，于是 `null.captchaRef` **抛异常**。

后果不是"这个弹窗坏了"，而是：

```
抛异常 → 中断整轮响应式刷新 → watch(isLoggedIn) 没跑到
      → view 停在 'register'，而 isLoggedIn 已是 true
      → 所有 v-if 分支都不匹配 → 弹窗只剩一个标题，内容全空
```

**一次 ref 回调抛错，打崩了一条完全无关的链路**（登录成功 → 切个人中心）。
现象极具误导性：注册明明成功了，界面却是空白 —— 看起来像注册接口坏了。

修法：**四个弹窗各挂各的**，`ref` 指向固定的那个组件，不存在"取值时机"的问题。
隐藏时 `UiModal` 的 `v-if` 不渲染内容，四个实例的开销可以忽略。

> 教训：**函数式 `:ref` 里不要解引用任何"可能已经变成 null"的状态**。
> 它有两个调用时机（挂载 / 卸载），第二时机往往在状态已经改了之后。

| 能力 | 说明 |
| --- | --- |
| **未读红点** | 服务端用 `users.replies_read_at` 当基准算 `unread`，**不建已读表** |
| **列表** | 谁、说了什么、在哪个页面、什么时候 |

**红点只在打开弹窗时取（`limit=1`）**：为了显示一个数字没必要把一整页回复
拉进浏览器。列表等用户真进去了再拉。

### 17.2 🔴 两个测试抓出来的真问题

**① 自己回复自己也会出现在「谁回复了我」里**

后端只判了"父评论是我的"，忘了排除**回复本身也是我发的**：

```sql
-- 原来
WHERE p.user_id = ?1 AND c.status = 1
-- 现在
WHERE p.user_id = ?1 AND (c.user_id IS NULL OR c.user_id <> ?1) AND c.status = 1
```

不改的话，用户给自己留的话会被当成"有人回复你"，还会把未读数顶起来。

`c.user_id IS NULL` 要保留：那是**账号体系之前**的老评论（没有归属），
它们不可能是"我"发的，该照常算作别人的回复。

**② 「我的评论」「谁回复了我」没有返回入口**

这两个列表页比个人中心深一层，但都只有"关掉整个弹窗"一条路 ——
用户想回去改个资料得重新开一遍。这个是 Playwright 测试撞出来的：
它点完「谁回复了我」再想点「我的评论」，发现个人中心那一列已经不在了。

已补「‹ 返回个人中心」，放在**顶部**（列表可能很长，底部要滚到底才够得着）。

### 17.3 反复跑测试撞出来的一个环境坑

账号端到端跑第二遍就开始**大面积 429**，文案是"**发**得太频繁了"。
先怀疑 `RATE_LIMIT_PER_HOUR`（本地已放大到 100000）—— 计数才 44，不对。
最后定位到 `POST /api/auth/login` 的**登录失败限流**：

```js
const ipFailBucket = `loginfail:ip:${ipHash}:${hourBucket(ts)}`
if (emailFails >= LOGIN_MAX_FAILS || ipFails >= LOGIN_MAX_FAILS * 4) return 429
```

`LOGIN_MAX_FAILS = 5`，即**同 IP 每小时只允许 20 次登录失败**。
而端到端要反复跑负向用例（错密码 / 未注册邮箱 / 已封禁），一会儿就打满。

**这个阈值当初漏了做环境变量覆盖**（其它限流都有，注释里也写明"本地放大阈值
就能稳定重复运行"）。已补 `AUTH_LOGIN_MAX_FAILS`，并在 `.dev.vars` 放大。

> 两个排查教训：
> 1. **文案相近但不同**：「请求太频繁」与「发得太频繁」是两处不同的限流，
>    我一开始按前者去查，方向就错了；
> 2. **限流计数不都是一样的量纲**：`rate_limits` 表里 `authcd:` 桶存的是
>    **时间戳**、`h:`/`d:` 桶存的才是计数 —— 直接按 counter 倒序看会看到
>    一串十亿级的数字，误以为限流爆了。

### 17.4 顺手修掉的两个测试写法问题

- **`FlClashCore`（代理软件）随机占用 Vite 的测试端口**，报

### 18.6 🔴 又一次栽在"端口动态挑"上：配置会在**每个 worker 里重新求值**

上一轮加的 `pick-port.mjs`（应对 Clash 随机占端口）有个致命缺陷：
它在**配置模块被求值时**现探测。而 **Playwright 会在每个 worker 进程里
各自求值一次配置文件** ——

```
worker 1 求值 → 4174 空闲 → 选 4174（随后起 Vite 占住）
worker 2 求值 → 4174 被占 → 顺延 4175
                ↓
一部分用例连 4174、一部分连 4175 → 大片 ERR_CONNECTION_REFUSED
```

**修法：结果必须落盘共享**。复用规则（兼顾"跨进程一致"与"上次剩的缓存不能用"）：

1. 缓存文件存在且**足够新**（< TTL）→ 直接用；
2. 缓存有点旧，但那个端口**正在监听**（多半就是我们这次起的 Vite）→ 用；
3. 否则 → 重新探测并覆盖缓存。

已验证：5 个独立进程求值得到同一个端口。

另外把端口缓存加进了 `.gitignore`（运行期产物，不该进仓库）。

> 教训：**"每次现算"这种看似更稳的做法，在多进程环境下反而是错的** ——
> 只要这个值会被多个进程各自算一遍，就必须有一处共享的真相。

### 18.7 测试写法的又一课

`toPublicUser()` 把 `id` 映射成了 `public_no` —— 所以**公开接口的 `user.id`
就是那 5 位对外编号**（内部自增 id 刻意不外露），而管理端接口才另外给 `publicNo`。
测试里读注册接口的返回值时用 `user.id`，我一开始写成 `user.publicNo`，
搜出来是 `undefined`。

搜索类断言还要注意：`stamp = Date.now().toString(36)` 在同一时间窗内**前缀相同**，
"搜这一条"会搜出两条。改成每条评论一个当轮唯一的标记。

## 20. 迁移演练抓出三个**只会在生产炸**的问题

### 20.1 为什么要做"演练"

生产库迁移是**不可逆的一次性动作**，而**本地开发库早就迁完了** ——
也就是说"迁移脚本还能不能跑"这件事，在开发环境里**永远测不到**。

所以写了 [`tests/migration/rehearse.mjs`](../../../tests/migration/rehearse.mjs)：从 git 取
**迁移前那一版 `schema.sql`**（`0c745272`），造一个临时库、灌几条真实形状的评论，
然后把迁移**真跑一遍**，并断言幂等性与数据完整性。

第一次跑就炸出三个问题，**全都是只在生产会出现的**。

### 20.2 🔴 建表顺序写反 → 账号功能整体不可用

原文件把 `ALTER TABLE users ADD COLUMN pw_salt` 写在
`CREATE TABLE users` **之前**。

- 本地：本地库早就建过 `users` → ALTER 正常 → **从没报错**；
- 生产：从来没有过 `users` → `no such table: users` →
  而 **D1 执行文件时一条失败就中止后续** → 四张表一张都没建。

**后果是账号功能整体不可用**，而且报错发生在迁移那一刻、离"你发现它不可用"还有很久。

### 20.3 🔴 索引建在加列之前 → 又带走三个索引

```
CREATE INDEX idx_comments_user ON comments(user_id);
```

而 `user_id` 是**下一步**才加的列 → 旧库上 `no such column: user_id` →
一条失败，后面三个索引全没建。

性能影响不致命（那两张表都很小），但"我的评论""谁回复了我"会退化成全表扫描，
而且**报错时机很晚**。

### 20.4 🔴 `schema.sql` 初始化全新库也是坏的

修完上面两个之后，演练的最后一步（"迁移后的结构与全新 `schema.sql` 比对"）
顺手发现：**`schema.sql` 自己就跑不起来**。

它的 `comments` 建表语句里**没有 `user_id`**（只在后面留了一句注释形式的 ALTER），
而文件末尾要在这个列上建索引 → 全新库执行到那里直接 `no such column: user_id`。

等于**"全新数据库初始化"这条路是坏的**。已把 `user_id` 写进建表语句。

### 20.5 修法：按依赖链拆成三步 + 让生产路径**零报错**

```
建表  ──→  加列  ──→  建（引用新列的）索引
 │           │              │
幂等      非幂等         幂等
```

| 文件 | 幂等 | 内容 |
| --- | --- | --- |
| `2026-10-05-auth-schema.sql` | ✅ | 四张表 + 不依赖新列的两个索引 |
| `2026-10-05-auth-columns.sql` | ❌（做不到） | `ALTER TABLE comments ADD COLUMN user_id` |
| `2026-10-05-auth-indexes.sql` | ✅ | 依赖 `user_id` 的两个索引 |

**还额外挪走了一条**：原来第 2 步里还有
`ALTER TABLE users ADD COLUMN pw_salt`，而 `users` 是第 1 步刚建的、**自带该列** ——
生产上会冒一条 `duplicate column name: pw_salt`。

> 迁移脚本"报了一条错但其实成功了"是**最坏的形态**：
> 操作者分不清"预期内的重复"和"真的炸了"，于是要么不敢往下走，要么忽略真问题。
> 所以那条挪成了文件末尾的注释（只留给"早期本地库"这种真需要它的场景），
> **生产路径现在三步全干净** —— 演练里有一条断言专门守着这一点。

## 21. 把"死链"这类问题做成自动检查

### 21.1 起因

上一轮那个**上线阻断级**的问题（必勾的「我已阅读并同意隐私说明」指向不存在的
`#/privacy`）有一个共性：**代码里写了一个目标，而目标不存在**。

这类问题**可以被机械地查出来**，不该指望"有人记得点一下那个链接"。
所以写成了单测 [`tests/unit/link-integrity.test.mjs`](../../../tests/unit/link-integrity.test.mjs)，
随 `npm run test:unit` 一起跑，查四类：

1. `href="#/xxx"` 指向的路由是否存在；
2. `<RouterLink to="/xxx">` 指向的路由是否存在；
3. `fetch('/api/...')` / `request('/api/...')` 在 `functions/api/[[path]].js` 里有没有对应分支；
4. `src` 里相对 import 能不能解析到文件。

### 21.2 第一版报了 60 多条误报 —— 教训比代码本身重要

第一版没做两件事，结果全是噪音：

- **项目大量省略扩展名**（`from '../utils/env'`，实际文件是 `env.js`），Vite 会解析；
- **`?raw` / `?url` 这类查询后缀**要先剥掉再判路径。

补上之后，从 60+ 条误报降到 **7 条**，再剥掉 `?raw` 就是 **0 条**。

> 教训：**误报比不查更糟**。一个报 60 条假问题的检查，几次之后就没人看了 ——
> 那时它连真问题也一起失效。写检查的时候，"不误报"和"能查到"一样重要。

## 22. 密钥体检：一个真的找到了东西的检查（以及它自己的一次假阴性）

### 22.1 起因

上线前该确认"开发期的密钥没有被写进仓库"。`.dev.vars` 是 gitignored 的，
但那只是**当前状态** —— 它保证不了某个值没被顺手写进别的文件。

做法：从 `.dev.vars` 取出**真实的值**，拿它们去 `git grep --fixed-strings`
搜所有被跟踪的文件。**只报告"有没有"，绝不打印值本身。**

### 22.2 第一次运行的结果

```
从 .dev.vars 读到 3 个敏感项（值不打印）： IP_HASH_SALT, AUTH_PEPPER, SALT_SECRET

❌ IP_HASH_SALT 的值出现在 1 个被跟踪的文件里：
     docs/HANDOFF.md
✅ AUTH_PEPPER 的值没有被任何被跟踪文件包含
✅ SALT_SECRET 的值没有被任何被跟踪文件包含
✅ .dev.vars 未被跟踪
```

**是虚惊**：HANDOFF.md 里那个值是 `local-dev-salt` —— 开发占位值，
本来就该给协作者看（HANDOFF 甚至顺带警告了"线上必须换成足够长的随机值"）。

但它暴露了我的检查不够聪明：**分不清"开发占位值"与"真密钥"**。
于是加了占位值识别 —— 然后踩了更大的坑（见下）。

### 22.3 🔴 更严重的坑：假阴性 —— 检查被静默降级成空操作

加了占位值识别之后，我按惯例验证"这个检查真的会红"：
把 `AUTH_PEPPER` 的**真实值**写进一个被跟踪的文件，跑测试 ——

```
未植入探针时：✅ 通过
已植入探针（docs/_leak-probe.md，值不打印）
植入后：❌ 竟然还通过 —— 这个检查是假的
```

**没红。** 诊断（只输出特征、不打印值）：

```
IP_HASH_SALT   长度= 14  被判定为占位值=true
AUTH_PEPPER    长度= 41  被判定为占位值=true     ← 41 个字符的密钥被当成占位值
SALT_SECRET    长度= 46  被判定为占位值=true
```

根因是占位值正则写成了：

```js
/^(local|dev|test|demo|sample|change|your|my|xxx|todo)/i.test(v)
```

用了 `/i` 又**没锚定整串** —— 于是任何以 `dev` / `my` 开头的值都算占位值。
41 字符的 `AUTH_PEPPER` 恰好中招，被从"待检查"降级成了"正常"。

**整个安全检查因此变成空操作** —— 报告一片绿，而真泄漏照过。

修法是**保守判定**（安全边界必须 fail closed）：

```js
// 只有两条窄规则：
//   1. 整个值就是一个已知占位词（锚定 ^...$）
//   2. 长度 < 12（真实密钥不该这么短）
// 拿不准一律算真密钥。
```

修完再验：

```
未植入探针时：✅ 通过
植入后：✅ 测试报错了（符合预期）
   报错内容：· AUTH_PEPPER → docs/_leak-probe.md
清理：文件✅ 已删除，git 索引✅ 已移除
```

> 教训：**假阴性比假阳性危险得多**。假阳性最多让人烦；假阴性会让人**以为查过了**。
> 而且这一条只有靠"故意破坏一次"才能发现 —— 检查全绿的时候，
> 你分不清是"真没问题"还是"检查根本没在工作"。
>
> 这也是第二次靠"验证检查本身"救回来（上一次是 link-integrity 的死链检查）。

### 22.4 ⚠️ 一处**我自己说过头了的判断**（已修正）

写这一节时我顺手写了一句"这暴露了一个**真实的**上线风险：`ADMIN_TOKEN=yxzm`
只有 4 个字符，而它是保护后台的唯一凭据"。**这句话是错的**，用户当场指出来了。

| 位置 | 原话 |
| --- | --- |

这两件事完全不同 —— 前者是**我的观测能力受限**，后者是**断言了一个我没证据的事实**。

> 教训：**"我验证不了"不等于"它是坏的"。** 把观测受限表述成风险，
> 是一种看起来负责、实际上会误导人的写法 —— 它会让人去改本来对的东西。
>

## 23. 🔴 本轮最重要的发现：`git push` 就是上线

### 23.1 怎么发现的

清点未推送的提交时想确认一件事：**推送会不会自动部署？**
翻 `wrangler.toml`，第一段注释就写着"站点用 **GitHub 自动部署**（origin: `Drloudx/syzg`）"。

**是。** 而且没有"再点一下发布"的中间步骤：

```
git push  ──────►  Cloudflare 自动构建部署  ──────►  线上生效
```

### 23.2 那风险有多大

新的**读评论 SQL 里就带着 `comments.user_id`**：

```
L346  SELECT c.id, c.user_id, c.nick, c.avatar, c.body, ...
L350  SELECT c.id, c.user_id, c.nick, ...
L389  SELECT c.id, c.user_id, ...
L396  SELECT c.id, c.user_id, ...
L583  INSERT INTO comments (page_key, parent_id, user_id, nick, ...)
```

而生产库**还没有迁移**（没有 `comments.user_id` 这一列）。

**所以现在直接 `git push`，整个讨论区会对所有人挂掉** ——
不只是登录用户，未登录的访客读评论同样走这条 SQL。

这是一个"**本该在推送那一刻才炸、而且炸得莫名其妙**"的事故：
本地一切正常、测试全绿、代码没问题，线上却整片评论读不出来。

### 23.3 但"先迁移"需要先证明一件事

直觉上当然该"先迁移、再推送"。可是这个建议要成立，必须先证明：

> **迁移对正在跑的旧代码没有副作用。**

否则"先迁移"反而会提前把线上搞挂（旧代码撞上不认识的列/表）。

**这件事不能靠推理。** 所以把旧提交（`0c745272`）里**真实的 SQL 形状**拿出来，
在迁移后的库上真跑一遍 —— 旧代码的写法是显式列出列名（不是 `SELECT *`），
且不写 `user_id`：

```sql
-- 读（旧）
SELECT c.id, c.nick, c.avatar, c.body, c.created_at, c.status, c.page_key, c.page_label
  FROM comments c WHERE c.page_key = ?1 AND c.status = 1 ORDER BY c.id DESC LIMIT 21
-- 写（旧）
INSERT INTO comments (page_key, parent_id, nick, avatar, body, status, created_at,
                      ip_hash, ua_hash, token_hash, review_reason, page_label) VALUES (...)
```

四条都验（读 / 写 / 改状态 / 删），并确认旧代码写入的行 `user_id` 为 `NULL`：

```
✅ 🔴 旧代码的读评论 SQL 在迁移后的库上仍可用
✅ 🔴 旧代码的写评论 SQL 仍可用（新列可空）
✅ 旧代码写入的行 user_id 为 NULL（新代码读它不会炸）
✅ 🔴 旧代码的改状态 / 删评论 SQL 仍可用
```

**结论（现在是实测的，不是推断的）**：迁移只做"新增"（四张新表 + 一个可空列 + 几个索引），
对正在跑的旧代码完全无影响 → **可以先跑迁移，再推送**。

运维手册的开头现在就是这一段，标题直接写 **「🔴 先读这一段：`git push` 就是上线」**，
并把"为什么可以提前跑迁移"的依据（引用上面那四条断言）一并写上。

### 26.2 🔴 坑一：挑中了**冻结的后台标签**

第一次跑，一上来就：

```

```

但手机是醒着的、CDP 也连得上 —— 很容易误判成"CDP 坏了"或"手机没醒"。

- `pickTarget` 把 `127.0.0.1` 与 `localhost` **归一化后**比较，并优先选"像站点本身"的

### 26.3 🔴 坑二：`Page.navigate` 只改 hash 不重载，于是"等到了却查不到"

修完上面那个，第 8 段报出一个**自相矛盾**的结果：

```
❌ 🔴 后台是独立外壳（盖住站点头部）     ← 查不到 .admin-shell
✅ 未填令牌时不露页签                    ← 页签数确实是 0（但页面坏掉时这条也会过）
```

可写探针去查，`.admin-shell` **明明在**（`hasShell: true`）。

**真因在我的测试脚本里**：

```js
await cdp.send('Page.navigate', { url: `${SITE}#/admin` })  // 只改 hash，不重新加载
await sleep(3000)
await ev(`localStorage.removeItem('myrzg:admin-token')`)
await cdp.send('Page.reload')            // ← 开始重载
await waitFor(`!!document.querySelector('.admin-shell')`)   // ← 命中的是重载前的旧文档
check(..., await ev(`!!document.querySelector('.admin-shell')`))  // ← 文档已换 → false
```

`waitFor` 与 `check` 之间**跨了一次文档替换** —— 一个说"有"、一个说"没有"。

修法是**一次干净导航**，不留窗口期：

```js
await ev(`localStorage.removeItem('myrzg:admin-token')`)     // 先在当前页清
await cdp.send('Page.navigate', { url: `${SITE}?t=${Date.now()}#/admin` })  // 整页加载
await waitFor(`document.readyState === 'complete' && !!document.querySelector('.admin-shell')`)
```

（cache-buster 必须放在 `#` **之前**，否则会被当成 hash 的一部分。）
