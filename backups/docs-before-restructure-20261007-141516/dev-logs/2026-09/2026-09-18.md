# 2026-09-18 开发汇总

## 性能（页面切换）

### 路由分包预取：消除手机端「先卡一下再切过去」

- 现象与根因（实测）：`router-view` 对懒加载路由会**等异步组件 chunk 下载完才挂载新页**，这段等待里旧页面一直挂在屏幕上不动。本机 localhost 实测切换 25~120ms（无感：`/recipes→/items` 新页 DOM 22ms / 内容就绪 97ms，最大帧停顿 70ms、零长任务），但 chunk 走网络后该延迟被放大，真机即用户感知的「卡一下」。
- 改动：`src/router/index.js` 新增两级预取（纯 `import()`，命中模块缓存，不执行页面组件）：
  1. `prefetchRouteChunks()` —— 首屏就绪后在 `requestIdleCallback` 中预取 17 个视图 chunk（约 282 KB 未压缩）；
  2. `prefetchDeferredRouteChunks()` —— 打开导航面板时补最重的 `/gacha`（单个 244 KB，占视图 chunk 近一半）。
- 触发点：`App.vue` 桌面骨架期结束处 / 移动端首屏就绪处各调一次 `prefetchRouteChunks()`；`NavigationMenu` 监听 `isOpen` 调 `prefetchDeferredRouteChunks()`。
- **并发下发会与首屏资源抢带宽**：一次并发 import 时，`卡池页资源全部可加载`（检查全部图片已解码）与 `魔物蛋卡池…`（蛋池封面解码）在并发测试下稳定失败。改为**串行 + 220ms 间隔**后 5 个套件 118 passed / 0 failed。
- 实测效果（生产产物 + CDP 网络节流，切换 `/recipes→/items|heroes|monsters|tasks`）：

| 网络 | 改动前 新页 DOM | 改动后 新页 DOM |
| --- | --- | --- |
| 本机 | 10~26ms | 11~24ms |
| 4G（RTT200/1.6Mbps） | **最高 9290ms** | **21~32ms** |
| 3G（RTT400/750kbps） | （超时） | 11~13ms |

- 首屏后已预取 17/18，`GachaView` 按设计延迟到导航意图，验证打开导航后其 chunk 才请求、随后切 `/gacha` 仅 34ms。
- 说明：预取解决的是「切换本身」的等待；页面**数据**仍按原逻辑在挂载后加载（4G 节流下约 3~6s），此时新页骨架已先显示，不再是旧页面僵住不动。

### 顺带修正的测试竞态

- `tests/ui/gacha.spec.js` 蛋池用例：切换卡池后封面是**新图**，原断言直接读 `naturalWidth` 而不等待，与图片加载赛跑（`openGacha` 的等图发生在点击切换之前，覆盖不到）。改为 `expect.poll` 等待解码完成——属测试竞态，不是页面缺陷。

## 性能（浏览器与 CDN 缓存）

### 新增 `public/_headers`（随构建产出到 `dist/_headers`）

- 背景（实测线上 `myrzg.yxzmy.top`，Cloudflare）：源站对**所有**路径都返回
  `Cache-Control: public, must-revalidate, max-age=0`，且 `must-revalidate` 下返回 **200 而非 304**（连测 3 次确认），浏览器无法复用、必须整份重传。图片另有 `max-age=3600`。
- 后果：每次重开 App / 刷新要**重下并重新 `JSON.parse`** 约 7 MB 数据
  （`items.json` 2.36MB + `heroes.json` 1.88MB + `tasks.json` 1.52MB + `monsters.json` 0.41MB + 其余），外加约 16 MB 字体。未走缓存的 `transferSize` 在刷新后逐项实测确认。
- 本项目其实**本来就具备可长缓存的条件**：`/assets/**` 文件名自带内容 hash；`/data/**` 的 JSON 按目录生成 manifest、URL 带 `?v=<该文件内容 SHA-256>`，且 `resourceClient.js` 会再校验 manifest 里的 sha256，不匹配即拒绝。缺的只是一个允许缓存的响应头。
- 新增 15 条规则（`_headers` 由 CF Pages 消费，`public/` 下随构建复制到 `dist/` 根）：

| 路径 | Cache-Control | 依据 |
| --- | --- | --- |
| `/index.html`、`/` | `no-cache`（+ `nosniff`） | 应用壳必须每次校验，否则拿不到新版本 |
| `/assets/*` | `public, max-age=31536000, immutable` | 文件名内容 hash |
| `/data/parsed/*`、`/data/dialogs/*`、`/data/taskDialogs/*` | 同上 | 各自有 `data-parsed-*` / `data-dialogs-*` / `data-taskDialogs-*` 清单校验，URL 带 `?v=` |
| `/data/notice.json` | `no-store` | 实时公告，不参与版本锁 |
| `/update/hotupdate.json` | `no-store` | **运行时热更清单**（`hotupdate.js` 的 `HOTUPDATE_MANIFEST_URL`），必须实时 |
| `/update/*.zip` | `public, max-age=31536000, immutable` | 热更包按版本号命名 |
| `/images/*`、`/ui/*`、`/fonts/*`、`/test2/*` | `public, max-age=604800` | 文件名**不带**内容 hash，资源维护会覆盖同名文件，故不给 `immutable` |
| `/_redirects`、`/_headers` | `no-cache` | 部署元文件 |

- 覆盖率核查（按 CF Pages 匹配语义模拟）：dist 内 **4803 个文件全部命中规则，0 个遗漏**（immutable 1640 / 7 天 3158 / no-cache 3 / no-store 2）。
- 格式核查：无 BOM、纯 LF、以换行结尾、15 条路径规则 + 17 条头行、仅用 `Cache-Control` 与 `X-Content-Type-Options`、无重复路径。

### ⚠️ 必须由你在控制台处理的点

**腾讯云 CDN 会覆盖本文件的策略。** 本文件只在 Cloudflare Pages 直接处理请求时生效。既然前面还有腾讯云 CDN，边缘缓存优先级更高——需在腾讯云 CDN 侧：

- 确认**「忽略查询字符串」为关闭**。否则 `?v=<hash>` 不参与缓存键，长缓存会读到旧数据（这是本方案唯一的正确性前提）；
- 配置对应的缓存过期规则，或对 `/data/`、`/assets/` 设置「遵循源站」。

### 缓存复用与传输量的权威实测（CDP）

用 CDP `Network.responseReceived.fromDiskCache` 判定（浏览器内部结论，不依赖跨域可见性），同一 URL 连测 3 次：

| 资源 | Cache-Control | 第 2/3 次请求 |
| --- | --- | --- |
| `/data/**` JSON | `public, must-revalidate, max-age=0` | ❌ 每次走网络 |
| `/fonts/*.ttf` | `public, must-revalidate, max-age=0` | ❌ 每次走网络 |
| `/images/**` | `max-age=3600` | ✅ disk cache |

用 CDP `Network.loadingFinished.encodedDataLength` 测**真实网络传输量**（手机视口，线上旧版站点，单次冷加载 `/recipes`）：

- 合计 **9608 KB / 43 个请求，0 个复用缓存**；
- 最大项：`/fonts/MYR2SansRegular.ttf` **6534 KB**、`/ui/map_w1_bg.png` 2423 KB、`/ui/logo.png` 121 KB；
- 旧版 `/recipes` 冷加载只需 ~20 KB 数据 JSON（`recipes.json` + `item-sources.json`），并非一次性拉全量数据表——**数据体积问题集中在物品/角色/任务等页**，不在首页。

据此两点确认：① `_headers` 要解决的正是「数据与字体零复用」；② 线上仍加载已废弃的 `MYR2SansRegular.ttf`（6.5 MB）与旧字体名，新版本已删除，**下次发布即省下这部分**。

### 测量方法教训（避免误判）

- **不要用 `Invoke-WebRequest` 判编码**：本次线上 `update/hotupdate.json` 被它报成「中文乱码」，实际原始字节是正确的 UTF-8（`E7 83 AD E6 9B B4 E6 B5 8B E8 AF 95` = 热更测试）。原因是响应头为 `Content-Type: application/json`（不带 `charset`），该工具按 Latin-1 解码。**结论：它显示的 `body` 串会失真，但 `Headers` 是可靠的。**
- **判 HTTP 缓存必须用 CDP 的 `fromDiskCache`**：`transferSize`/`decodedBodySize` 在跨域且无 `Timing-Allow-Origin` 时会把 `transferSize` 记成 0，容易误判为「已缓存」。
- 本次还出现过两次**无效路径取样**（用本地构建名 `/assets/index-*.js`、以及线上尚未部署的 `/images/gacha/shop.png` 去探测），返回的 507 字节其实是 SPA fallback 的 index.html。**探测线上资源前要先确认该文件确实存在。**

## 性能（资源体积）

### 字体转 WOFF2（无损，省 47%）

- 背景：`HarmonyOS_Sans_SC_Regular/Bold.ttf` 各约 7.9 MB（CJK 全字集 **29221 个字形**），首次加载经 Brotli 后仍各 ~5.4 MB，占手机端首屏传输 **13836 KB 的 78%**（实测 CDP `encodedDataLength`）。缓存生效后 reload 为 0 KB，所以成本只在新用户首次。
- 全站实际只用到 **3533 个唯一字符（12.1%）**，但**未做子集化**——子集化会缺字回退设备字体，可能同段中文出现两种字形，风险由用户判断后选择不做。
- 新增 `scripts/dev/convert-fonts-woff2.mjs`（默认只预览，`--apply` 才写文件；自检 fonttools/brotli 依赖）。**不裁字形、仅换容器**，因此无缺字风险。
- 结果：`7.88 MB → 4.08 MB`、`7.78 MB → 4.20 MB`，合计 `15.66 → 8.28 MB（省 47.1%）`。
- `theme.css` 的 `@font-face` 改为**优先 WOFF2、TTF 兜底**：`src` 按 `format()` 择一，浏览器只下载一种。实测线上页面字体请求 `woff2: 2 / ttf: 0`，确认不会两个都取。

#### 容器选型：Ogg/Opus → **MP4/Opus**（重要，勿改回去）

最初按「Opus 就用 `.opus`」的习惯产出 Ogg 容器，Chromium 验证 19/19 通过**但那是漏测**：补测 WebKit（Safari/iOS 引擎）后发现放不出来。三家引擎用**真实播放**实测：

| 容器 | Chromium | WebKit(≈Safari/iOS) | Gecko | 体积 |
| --- | --- | --- | --- | --- |
| Ogg/Opus（初版选的） | 可播 | **不可播** | 可播 | 基准 |
| WebM/Opus | 可播 | **不可播** | 可播 | 相同 |
| **MP4/Opus（最终）** | 可播 | 可播 | 可播 | 基本相同 |
| MP3（备选，未采用） | 可播 | 可播 | 可播 | 更大且质量更低 |

- 结论：Opus **编码**三家都支持，是**容器**决定成败。Ogg/WebM 里的 Opus 在 WebKit 是编码层拒绝（`canPlayType` 返回空、解码 `MEDIA_ERR_SRC_NOT_SUPPORTED`；WebM 则 `readyState` 卡 0、`duration` 为 NaN）。MP4/Opus 体积与 Ogg 基本相同（`gacha_shop` 1026 KB → 1035 KB）却多覆盖 Safari/iOS，故改用 `.mp4`。
- `.m4a` 后缀**不可用**：ffmpeg 会因此选 `ipod` muxer，而它不支持 Opus（报 `codec not currently supported in container`）。必须用 `.mp4` 走通用 mp4 muxer。
- 两个**判据陷阱**（本机各踩一次，已写进脚本文件头）：
  1. **`canPlayType` 不可信**：WebKit 对 `audio/webm; codecs=opus` 谎报 `probably`，实际放不出来。不能用它选容器。
  2. **`canplaythrough` 不可用于短音效**：WebKit 对 1~2s 音效明明已解析出元数据、`readyState=3`，却始终不触发该事件，会得到 **8/19 假失败**。有意义的判据是 `play()` 后 `currentTime` 是否推进——按此判定三引擎均 **19/19 通过**（headless 无音频设备，用 `muted` 规避自动播放策略，播放进度与解码仍推进）。
- 最终验证：三引擎（Chromium 152 / WebKit 26.5 / Firefox 153）**19/19 真实播放推进**，页面自身请求 0 次错误扩展名、响应 200/206 且无 html 假成功（dev server 对不存在路径会回 200 + `text/html`，故状态码 200 不能当成功）。`Content-Type: audio/ogg` 变 `video/mp4`，浏览器按内容探测，不影响播放。
- 缓存：URL 由 `env.js` 的 `getImageUrl` 拼 `?v=<RESOURCE_BUILD_ID>`，且本次是**改扩展名**（URL 字符串本身变化），不存在旧缓存命中风险。`public/_headers` 的 `/images/*` 规则同样命中 `.mp4`（7 天、不带 `immutable`，适合「同名可覆盖」的素材）。

### 图片版本号改为逐文件内容哈希（跨部署复用缓存）

- 问题：原先 `getImageUrl` 用全局 `__RESOURCE_BUILD_ID__`（含 `Date.now()`）当版本号，**每次构建所有图片 URL 都变**，哪怕图片一个字节没改 → 部署一次全体用户的 `/images` 缓存全部作废。
- 改法：`vite.config.js` 新增 `collectImageVersions(publicDir)`，构建时算出 `public/images/**` 每个文件的 SHA-256（取前 12 位），经 `__IMAGE_VERSIONS__` 注入；`env.js` 的 `getImageUrl` 优先用**该文件自己的哈希**，未收录的路径回退 `RESOURCE_BUILD_ID`（保持旧行为，不会漏掉刷新）。`/ui/` 前缀仍不做版本化（维持原状，避免行为漂移）。
- 实测（生产产物，19 个路由）：一个页面 55 张图出现 **54 种不同版本号**（全局 build id 只会有 1 种）；抽样 4 张用本地文件独立复算 SHA-256 **4/4 匹配**，确认版本号确为内容哈希。
- **代价（诚实记账）**：版本表 3067 条 / 176 KB 未压缩，落在 `ui-*.js`（该 chunk raw 230 KB / gzip 57.4 KB，此前为 54.49 kB raw / 18.87 gzip），即首屏约 **+38 KB gzip**。换来的收益是未改动图片跨部署不再重下。
- 注意：该功能**只在生产构建生效**（`define` 在 `apply: 'build'` 的插件里），dev server 下 `getImageUrl` 不带 `?v=`——验证必须在 `vite preview` 或线上做，dev 下测会误判为「没生效」。

## 重构与维护

### `.git` 体积治理：历史重写（698.7 MB → 146.4 MB）
- 起因：`.git` 高达 698.7 MB。诊断发现**单个 pack 就 696.8 MB**，而 `HEAD` 树仅 162.4 MB → 约 534 MB 是**历史积累**（曾被提交、后被删除或替换的旧文件）。
- 历史中的大头（按 blob 体积）：`public/images/chara.zip` 97.4 MB、`node_modules/**` 约 110 MB（3413 个路径，历史上被提交过，现已在 `.gitignore` 中）、gacha WAV 66.4 MB、已弃用字体 `MYR2Sans*.ttf` 18.9 MB、`public/update/*.zip` 7.6 MB。
- **诊断方法上的教训**：第一版分析脚本把每个 blob SHA 只映射到**一个**路径（`rev-list --objects --all` 里同一 blob 可能出现在多个路径，Map 后写覆盖前写），于是「HEAD 仍在用」判定全错，得出「可回收 0 MB」的荒谬结论。第二版改用**集合差**（`--all` 可达 blob − HEAD 可达 blob）才正确。**不要用单值路径映射判断对象是否活跃。**
- 工具：`git-filter-repo`（本机无，经 `python -m pip install git-filter-repo` 安装；git 2.54 满足 ≥2.22 要求）。
- 方案（用户选定）：`--strip-blobs-bigger-than 100K --path-glob '*.ttf' --invert-paths --force`。注意该参数**不接受小数**（`0.1M` 会报 `invalid literal for int()`），须写 `100K`。
- **重大陷阱（务必记住）**：`--strip-blobs-bigger-than` 会把**当前 HEAD 提交**里超过阈值的 blob **一并剥离**，不只是历史。结果：HEAD 树从 5185 文件 / 162.4 MB 缩到 4924 文件 / 46.1 MB，**工作区同步缺文件**；而 `git status` 显示**干净**——因为 HEAD 与工作区都缺这些文件，两边"一致"，具有极强误导性。**必须重写前先备份 HEAD 中超阈值的文件，重写后补回。**
  - 本次重写前已把 HEAD 中 260 个 >0.1MB 文件（100.7 MB）保存到临时目录（首次因 `git ls-tree` 默认转义非 ASCII 路径、中文文件名复制失败，加 `-c core.quotepath=false` 后 260/260 成功），重写后补回 258 个并单独提交（`fix(repo):` 提交）。
- **另一个失误**：filter-repo 会移除 `origin` 远端。我恢复远端后执行了 `git fetch origin`，把**未重写的远端历史（含全部大对象）**又拉回本地，`.git` 从 90.3 MB 反弹回 698.5 MB。真正让旧对象存活的是 `refs/remotes/origin/main` → `c2e5391`。删除该远程跟踪引用 + `git reflog expire --expire=now --all` + `git gc --prune=now` 后降到 **146.4 MB**。
  - 教训：**历史重写后不要 fetch 原远端**，否则等于把刚清掉的对象再下载一遍。若确需保留远端跟踪，接受体积反弹；若以体积为先，删掉远程跟踪引用。
  - 另：`git update-ref -d refs/remotes/origin/main` 后残留了 `refs/remotes/origin/HEAD` 符号引用（指向已删分支），`git fsck` 报 `invalid sha1 pointer 0000...`；删除该文件后 `fsck` 干净通过（exit 0）。
- 结果：**`.git` 698.7 MB → 146.4 MB（−79%）**，`git fsck` 通过，工作区干净，HEAD 5172 文件。
- **代价与后果（重要）**：历史重写改变了**全部提交的哈希**，本地与远端已**完全分叉**（`git merge-base` 无共同祖先）。因此**推送必须 `--force`**，且会覆盖远端历史；其他克隆此仓库的协作者需要重新克隆。用户尚未推送。

| `/ui/*` | `max-age=3600` | **线上是旧版**（本地为 604800） |
| `/test2/*` | `max-age=3600` | **线上是旧版**（本地为 604800） |

即线上跑的是本轮之前那版 `_headers`。**这不影响目标能力**：`/assets/*` 与 `/data/*` 两条已按内容寻址长缓存，而 `/ui/*` 是「随热更包内置、不打 CDN」的 UI 图标、`/test2/*` 是导出示例目录，都不在「靠 CDN 更新手机端」的路径上。顺带发现 `/_headers` 请求本身被 SPA fallback 返回 `index.html`（静态文件不暴露），但它**确实生效**——`/`→`no-cache`、`notice.json`→`no-store` 只可能来自它。

**浏览器侧缓存复用实测**（CDP `Network.requestWillBeSent` + `requestServedFromCache`）：

- 冷缓存首次访问：157 个资源响应，命中 0。
- 同 context 内 reload：**153~154/157 命中**；`/assets/` 56/56、`/images/` 89/91、`/ui/` 7/7、`/data/` 2/3。
- 未命中的 3 个**全部合理**：`/data/notice.json` 按设计 `no-store`；两张 `Common_ItemIcon` 图片返回 **304**（协商缓存命中，不是下载——服务端不会对无缓存的请求回 304；EdgeOne 未在 304 中回 `cache-control`，故 CDP 未标记为 disk cache）。

**两个测法坑（都踩过，勿重犯）**：

1. Playwright 每个 `BrowserContext` 拥有**独立缓存**，`browser.newContext()` 再访问测不出复用（实测两遍均 0 命中），必须在同一 context 内重复导航。
2. 同 URL 只改 hash **不会重新导航**（响应 0）；且**磁盘缓存命中时 `Network.responseReceived` 不触发**，只看该事件会把「没请求」误读成「没缓存」。须用 `requestWillBeSent` 统计请求、`requestServedFromCache` 判断命中。

**端到端结论（为何「改网站 = 手机端更新」成立）**：

- `resourceClient.js` 的 `fetchResource` → `expectedHashFor(path)` 读 `assets/data-manifests/*.json` 取该文件的 **SHA-256** → `withVersion(url, hash)` 拼 `?v=<hash>`。新数据 → 新哈希 → **新 URL** → CDN 与浏览器都必然 MISS。
- `isDev` 绑定 `import.meta.env.DEV`，生产构建为 `false`，因此**不会**退化成 `?v=<时间戳>` 打穿 CDN 缓存（这是本链路最需要确认的一点）。
- 原生端 `getResourceBaseUrl()` 在线返回 `CLOUD_URL`（`https://myrzg.yxzmy.top`），离线返回空串走包内 `dist`；远端失败由 `onFallback` 回退本地。
- **能力边界**：`capacitor.config.json` 的 `webDir: "dist"` 意味着 **JS/CSS 代码随 APK 内置**，只有 `/data/**` 与 `/images/**` 走 CDN。故「只更网站」能更新**数据与资源**，**代码变更仍需热更包或新 APK**。
